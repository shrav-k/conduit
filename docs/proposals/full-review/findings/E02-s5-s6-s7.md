## FR-393

**S7 as designed cannot show that an outsider can write a package from spec/ alone**

E02 I1 · assessment · verifier: partly · decides: owner

The claim S7 exists to test: someone who did not build Conduit can, from the specification, put an existing MCP server and a small piece of their own code behind Conduit as installable packages that agents then use under Conduit's access rules. If it is false, ruling 40's provider layer ("a contract that any existing tool can implement") and ruling 47's publication condition (an outside author builds and uses an integration through the public contracts) both fail. No other scenario tests whether anyone but the project can use the specification.

The design can pass with the claim false, for five reasons.
1. Help has no limit. P3 passes when the packages install and work; "any extra guidance is recorded as intervention", and no number of interventions fails the run.
2. The existing server is not one. Order 103 chose the server for a corner case (a command that repeats a named argument), so the accepted first candidate is mcp-remote, a proxy with no tools of its own, in front of an upstream stub that the harness builds. The contracts the author writes therefore describe one tool the project wrote: reading a named synthetic fixture. A real server's tool schemas never meet Conduit's schema profile. The candidate was also chosen "from remembered CLI shapes, without network access".
3. Much of it is not the author's work. The conflicting selector, the non-matching node and the ambiguous binding are prepared by the harness and only submitted by the author, so P5 and half of P4 test the engine's admission, which vectors already partly cover. The other half of P4 ("record whether existing packaging conventions suffice, or leave the author task blocked") cannot fail.
4. One author, of the same vendor as the builders. The author is one fresh Codex session, on an engine that Codex workers built; a reading of an unclear promise that Codex makes consistently stays invisible. The independent builds use two vendors. The pack is also not spec/ alone: it adds a task brief and the CLI reference, both written inside the project, and the author must install the two Agent packages, whose archives are worked examples; the text does not say whether the author may read them.
5. It can fail with the claim true. P3 needs real Claude Code and Codex Agents on the second accounts to use the packages, so a sign-in fault, or an Agent turn that outlasts its deadline (seen in S1's fresh-author run), fails a run whose packages are sound.

Per pass condition: P1 and P2 are the ruled gate and pass whenever vectors pass. P3 carries the claim, with the faults above. P4 and P5 exercise code. P6 (a non-Rust plugin published on npm) is a publication check, not a condition of v0.

Per measure: all three were defined before any run. M0 (the first build's table, by reference) is countable for files and lines; "concepts met" and "mistakes" need a judge. M1 is D01, defined only in S2's text, and when S7 was drafted that text was still a placeholder; its three rows (plain server, adapter, Conduit-aware) fit S2's real service and are contrived here. M2 (rejections, diagnostics, corrections, interventions, argv positions) is countable from logs and is the measure to keep, once "intervention" is defined.

What works: the author's isolation from history, the handoff to a clean consumer project (T6), which leaves an artifact a third party can install again, and the honest Limits section.

## FR-396

**S6: the right claim and the best measure, one condition that can pass while false, and the longest queue**

E02 I4 · assessment · verifier: partly · decides: owner

Claims, and what would be false if each failed.
- P2: once a Conduit is closed, nothing more is dispatched through it or for work it began (new requests, repeats, onward requests), and the call already in flight still returns its true result. If false, a revocation does not stop running work, or it destroys the true outcome.
- P3: retiring a Resource closes access to it at once, and its shutdown is reported confirmed only when it is. If false, calls reach a retiring Resource, or Conduit reports a stop that did not happen.
- P4: retirement runs the retire hook, then the stop whatever the hook did, and touches nothing the instance does not hold.
- P5: a Pool retires its members in dependency order, and a failure holds back only what depends on it.
This is the purpose's own claim (preservation test 2: every access can be inspected and revoked), under load.

Pass conditions.
- P1: the ruled gate; it passes whenever the vectors do.
- P2 tests its claim. Its measure M1, the count of dispatches after a close or a retirement against the fixture's own ledger, is independent, countable and has an expected value of zero: the best measure in the three scenarios. It can pass falsely only for chains it does not build. Its task-fetch branch rests on MCP's tasks extension, still beta, and on a relay that is not built (two large orders in S4's plan).
- P3 can pass with the claim false. Every fixture is a well-behaved server. Two facts the engine's own conformance document states are in no branch: the built-in runner reports a run stopped right after signalling the kill, not after seeing the exit, and a child that leaves the process group survives. The second was seen in dogfooding with Codex's terminal children. A shutdown reported confirmed while such a child still writes is exactly the wrong result P3 exists to catch.
- P4: the order of hook and stop is tested. "Erases no backing data" passes trivially, since the engine cannot reach the fixture's ledger, and "stops only what the instance holds" rests on one neighbour.
- P5 mostly repeats what LIF-021's 11 existing vectors show. The order among unordered and cyclic members is the engine's own choice (DL1), so judging it tests no promise.

Measures. All were defined before any run. M0 is by reference; with no bar and no baseline, nothing it reports can fail S6. M1 and M2 are countable by a third party from the dispatch log, the records and the ledger, once "retained record/data checks" is a fixed list.

Scripted and real clients. The README is right that no engine observation here needs a real client, and no real-client run is planned, so none adds cost. Two things only a real client shows: whether the in-flight result still reaches the model when its tool list changes under it (experiment 008's cases all start the call after the close), and what a real Agent's processes do when the Agent itself is retired in mid-invocation (T4).
