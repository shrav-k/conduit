## FR-406

**S10's runtime swap already fails the 'no edit to any other document' test on paper**

E03 I1 · assessment · verifier: supported · decides: owner

The specification lets each runtime provider choose which implementation items it runs (PRV-012, after Nomad's task drivers). It also forbids every provider except the engine's own runner from running a `command` item at a relative path (PRV-007).

Every runnable item the scenarios use is of a form only the engine's own runner accepts:
- S1's filesystem server is an npm `package` item.
- Both Agent packages, both S2 Linear servers and S4's effect servers are relative `command` items.

Of the two runtime providers that exist, the local-process provider (A63-RP1) runs only absolute-path commands; npm waits for A63-RPN, which is unwritten. The SSH provider runs only absolute or bare commands. Docker is not built.

So moving S1 or S2 to a provider behind the runtime contract means rewriting the item in each service's and each Agent's package manifest. Those are other packages' documents, which is the edit the swap test forbids. Separately, `runtime` may be written only on an instance (PLC-005; POOL-009 allows a Pool input with no default), so leaving the engine's runner also edits every instance document: two Resources and two Agents in S1.

The accepted pre-registration absorbs both. It lists 'instance `runtime` selections' as allowed, and it moves the item conversion 'before freezing the comparison' as provider preparation. P4 can therefore pass while the roadmap's claim, 'the same documents behave the same on either', is false for the documents S1 passed with.

The paradigm gap is specific. Kubernetes swaps a runtime with no workload edit because every CRI runtime runs one unit, the OCI image, and the node has a default handler. Conduit's items follow Nomad's drivers, where a job is tied to its driver and nobody claims portability.

What I would change: fix what a passed swap means (I2), and count the edits on paper before building more for S10 (I5). If the owner wants the strict test to pass for runtimes, the language needs one item form that every runtime provider must run. Otherwise the specification should state the limit.

## FR-409
