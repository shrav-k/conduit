# Naming precedents and semantic differences

Research date: 2026-11-04. These comparisons concern terminology, not adopting another runtime.
Source descriptions are attributed below; the “Conduit implication” column is our analysis.
Candidate words remain unaccepted. See [source boundaries](SOURCES.md) and the
[accepted vocabulary map](../../VOCABULARY.md).

## 1. Orchestration, deployment and packaging

| System and source terms | Meaning in the inspected source | Conduit implication |
| --- | --- | --- |
| [Kubernetes objects](https://kubernetes.io/docs/concepts/overview/working-with-objects/): object, manifest, spec, status | Objects record intent; spec describes desired state and status reports observed state. A manifest is an authored representation. | Useful separation of definition and observation. Calling all instance configuration “desired state” would misdescribe confirmed control changes. A manifest is a document, not another family. V01, V15–V16. |
| [Kubernetes controllers](https://kubernetes.io/docs/concepts/architecture/controller/): controller, control loop | Controllers repeatedly act to bring current state toward desired state. | Reserve “controller” for code that actually implements such a loop. Our “control” is a supported operation, not automatically a controller. V13–V14, V30. |
| [Docker](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-an-image/): image, layer | An image packages files, binaries and configuration; images are immutable and assembled from filesystem layers. | The reusable-definition analogy helped the design. “Image” would now imply packaging and filesystem behavior absent from many templates. Do not rename templates or retained graphs to images/layers. V01, V06, V32. |
| [Compose](https://docs.docker.com/compose/intro/compose-application-model/): service, network, volume, project | Services define application components; networks connect them; volumes provide persistent filesystem storage. A project groups one application deployment. | Name responsibility separately from realization. A Pool is not merely a deployed application, and offering Resource templates does not deploy them. Compose merging rules are not ours. V01, V13, V34. |
| [Helm](https://helm.sh/docs/topics/charts/): chart | A chart packages files describing related Kubernetes resources, with explicit chart metadata and a conventional layout. | A branded package noun can be memorable, but “chart” adds little for our code-optional exports. Keep package, template and instance distinct; do not use one name for all three. V06–V08. |
| [Nomad](https://developer.hashicorp.com/nomad/docs/glossary): job, task group, allocation, node pool | Jobs express desired workloads. An allocation maps a task group to a client node; node pools group execution machines. | “Allocation” clearly describes placement, not a reusable definition. Conduit's Pool groups/owns domain Resources rather than necessarily computing capacity. Avoid importing “job” for every invocation or “node” for both a graph step and a machine. V10, V26, V30, V34. |
| [Tilt](https://docs.tilt.dev/tiltfile_concepts.html): resource, Tiltfile | A resource groups build/deploy/runtime pieces for development feedback. A Tiltfile executes configuration logic and records file accesses for reevaluation. | Similar UI presentation does not make Tilt's resource boundary our unitary Resource. “Watch” and “reload” imply behaviors we must declare, not infer from using YAML. V03, V15, V29. |
| [containerd scope](https://github.com/containerd/containerd/blob/8a9c72699b5a29daa94cbf1bfe270f1bd1b52d12/SCOPE.md): primitives, extension points, implementations | Its scope emphasizes independently usable components, shared primitives and interchangeable implementations at defined boundaries. | A good naming model for contracts versus implementations. A common word should identify a stable responsibility rather than a particular crate or process arrangement. V04–V06, V30. |
| [OCI Runtime Specification](https://github.com/opencontainers/runtime-spec/blob/main/spec.md): configuration, execution environment, lifecycle, bundle | The specification distinguishes these aspects of running containers. | “Runtime” is an execution implementation in this domain. Qualify the whole Conduit runtime versus an instance's managed runtime declarations. No container or sandbox guarantee follows from our word “instance.” V13, V30. |
| [OpenTofu](https://opentofu.org/docs/v1.11/language/providers/requirements/): provider requirement, source address, local name | A dependency has an external source identity, a local name and a version constraint. | Supports keeping dependency aliases separate from artifact identity and exported names. “Provider” is already overloaded by model vendors and Conduit endpoint roles; avoid making every implementation a provider. Exact-version rules remain ours. V08, V23, V32, V37. |
| [Pulumi](https://www.pulumi.com/docs/iac/concepts/inputs-outputs/): Input, Output | Wrapped values preserve Resource dependencies so infrastructure changes can be ordered. | “Input/output” is useful and recognizable. Our bindings have explicit forms and validation; they are not Pulumi language objects or promises, and do not import desired-state reconciliation. V11–V12. |

## 2. Contract and configuration languages

| System and source terms | Meaning in the inspected source | Conduit implication |
| --- | --- | --- |
| [WIT](https://component-model.bytecodealliance.org/design/wit.html): package, interface, world, import/export, resource | A world describes a component's imported/exported contract; interfaces group functions/types. Resources expose behavior through owned/borrowed handles. Packages collect definitions. | Strong precedent for explicit public contracts and scoping. Do not call our capability an Interface or a managed handle a Resource: both collide with settled families. “World” is evocative but would introduce another umbrella without a clear job. V02–V08, V28. |
| [Smithy](https://smithy.io/2.0/spec/service-types.html): service, operation, resource, shape | A service aggregates operations/resources as an API entry point; shape references express the model. | Keep “operation” for callable behavior. “Shape” emphasizes data modeling, whereas our contracts also govern effects and recovery. “Service” should not substitute for every Resource or package. V02–V04, V09. |
| [YANG 1.1](https://www.rfc-editor.org/rfc/rfc7950.html), §§4.2, 7.12: module, grouping, uses, rpc, action | Modules collect definitions; groupings can be reused without independently adding data nodes. Operations can be top-level RPCs or actions tied to data nodes. Configuration and state are distinguished. | Reusable definition versus realized data is a valuable distinction. A composed requirement need not be a new live object. “Action” is a plausible alternative to operation, but does not inherently explain effects or completion. V02, V09, V15, V17. |
| [NMDA](https://www.rfc-editor.org/rfc/rfc8342.html), §5: candidate, running, intended, operational | These datastores distinguish editable configuration, transformed intent and operational information; “running” does not simply mean fully applied. | Strong warning against assuming “current,” “running” and “applied” are synonyms. Our confirmed configuration, outstanding request and observed state should stay explicit. We are not adopting NMDA datastores. V15, V29. |
| [TOSCA 2.0 CS01](https://docs.oasis-open.org/tosca/TOSCA/v2.0/cs01/TOSCA-v2.0-cs01.md), §§3.1–3.5: node/relationship templates, capabilities, requirements, interfaces, workflows | Topology models components and relationships. Requirements connect needed features to capabilities. Workflows perform operations; operation implementations are distinct from topology descriptions. | The closest structural naming comparison for relationships versus establishment. Our composable requirements include ongoing duties, not just dependency satisfaction. A Conduit is not the setup workflow. “Node” or “Interface” would conceal important differences in our vocabulary. V03–V04, V10, V17, V23–V24. |
| [JSON Schema 2020-12](https://json-schema.org/draft/2020-12/json-schema-core): schema, vocabulary, dialect, instance, annotation | Vocabularies define keywords and semantics; dialects select vocabularies. “Instance” means the JSON value under evaluation. | Keep external words unchanged and qualify them where needed: “schema instance” versus “Resource instance.” A data schema is one part of a Conduit contract, not the entire behavioral contract. V01–V02, V15. |
| [CUE](https://cuelang.org/docs/reference/spec/): value, constraint, unification | Values participate in a lattice; unification combines constraints formally. | “Constraint” can be an accurate narrowing term, but may suggest a solver or algebra we have not promised. Individually enforcing composable requirements does not imply a general unification engine. V17–V18. |
| [CEL](https://github.com/cel-expr/cel-spec/blob/21ec6f4e52e8d694687ff9ed7408d3eccbb955d7/doc/langdef.md): expression, program, evaluation | CEL describes terminating, side-effect-free evaluation with optional static checking. | Use “expression” carefully: our value bindings select or assemble values, while transformations use operations. Calling every binding an expression invites unsupported computation expectations. V11. |
| [Dhall](https://docs.dhall-lang.org/discussions/Safety-guarantees.html): configuration language, imports | Dhall explicitly bounds computation and external interactions, including import behavior. | An attractive authoring name must not imply arbitrary evaluation/imports. Our YAML/JSON boundary and supplied schema dependencies are already settled. This naming inquiry does not reopen language selection. V02, V08, V11. |

## 3. Executable composition and dataflow

| System and source terms | Meaning in the inspected source | Conduit implication |
| --- | --- | --- |
| [CWL](https://www.commonwl.org/v1.2/Workflow.html): process, workflow, step, data link, source/sink | A workflow connects subprocess outputs to downstream inputs as a DAG; independent steps may execute concurrently. Data links describe value movement. | Strong support for “step” and “input/output.” “Workflow” is viable if we state the finite dependency semantics. “Source/sink” is useful for directed value flow, not a universal designation of bidirectional Conduit peers. V09–V12, V23. |
| [Tekton Pipelines](https://tekton.dev/docs/pipelines/pipelines/) and [TaskRuns](https://tekton.dev/docs/pipelines/taskruns/): Task, Step, Pipeline, TaskRun | Definitions and executions have distinct names. Tasks contain container-image steps; TaskRuns execute them, and Pipelines arrange tasks. | The definition/execution distinction is useful. We need not copy its hierarchy or create another object family for every graph execution. Conduit steps need not be containers. V09–V10, V26. |
| [Argo Workflows](https://argo-workflows.readthedocs.io/en/latest/workflow-concepts/): Workflow, template, entrypoint | A live Workflow object contains the definition and execution state; templates and an entrypoint specify work. | “Template” is not equally scoped across systems: Argo uses it for execution components as well. Keep our reusable family templates distinguishable from graph-backed operations. V01, V10, V26. |
| [Temporal Workflow Execution](https://docs.temporal.io/workflow-execution), [Activity Execution](https://docs.temporal.io/activity-execution): definition, execution, activity, worker | The platform separates workflow definitions from durable executions and dispatches activity work with lifecycle/retry handling. | Precise definition/execution terminology is valuable; “durable workflow” also carries strong recovery expectations. Our retry/recovery contracts must not become an implied Temporal guarantee, and “activity” adds little over operation. V09–V10, V26, V30. |
| [Prefect](https://docs.prefect.io/v3/concepts/flows): flow, flow run | A flow is authored as a decorated Python function; one invocation is represented by a flow run with tracked state. | A clean noun pair, but “flow” would compete with the ongoing Conduit relationship. Prefer not to call both finite setup and ongoing exchange a flow. V10, V21, V26. |
| [Node-RED](https://nodered.org/docs/user-guide/concepts): node, wire, message, subflow, config node | Messages trigger nodes, wires carry messages, subflows package nodes for reuse, and config nodes share configuration such as a broker connection. | Excellent visual inspiration for composing smaller pieces. It is an event-driven system, not our finite setup graph. A reusable graph-backed operation should not imply a new running node or universal message payload. V05, V10–V12. |
| [Apache NiFi](https://nifi.apache.org/docs/nifi-docs/html/overview.html): FlowFile, Processor, Connection, Process Group, Flow Controller | FlowFiles carry content/attributes; processors operate on them; connections act as queues; the controller manages execution. | Role-specific nouns explain data movement. Calling a Conduit a queue or a setup graph a continuous pipeline would imply the wrong persistence/backpressure model. V10, V21, V28. |
| [GStreamer](https://gstreamer.freedesktop.org/documentation/application-development/basics/elements.html): element, source, sink, pad | Elements perform media work and expose input/output pads; sources produce data for the pipeline. | Shows why short technical terms can work when narrowly defined. “Pad” would impose unnecessary learning; “port” risks confusion with network ports. Prefer named inputs/outputs unless the protocol actually needs another port abstraction. V12, V23. |

Do not use “connection closed” without saying whether the socket or logical participation ended. TCP delivery does not prove an application operation completed. V21–V23, V26. |
| [QUIC, RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html): connection, stream | QUIC multiplexes ordered byte streams within a connection, with stream-level lifecycle. | Demonstrates that stream and connection are different scopes. “Stream” should describe a capability with declared sequencing, not every Conduit. | [NATS streams](https://docs.nats.io/learn/jetstream/your-first-stream), [pull consumers](https://docs.nats.io/learn/jetstream/pull-consumers): subject, stream, consumer, fetch/consume | Streams retain messages selected by subject. Pull consumers support bounded fetches or continuing consumption. | Separate retained history from how a reader retrieves it. “Consumer” is a role, not necessarily an autonomous process or Agent. The example does not imply Conduit acknowledgments mean model comprehension. V21, V23, V33. |
| [Kafka 4.1 introduction](https://kafka.apache.org/41/getting-started/introduction/): event, topic, partition, producer/consumer | Topics retain events and partition them for placement and throughput; ordering is tied to partitions. | “Topic” is suitable only for a domain capability that means it. | [Signal Sesame, revision 2](https://signal.org/docs/specifications/sesame/): session, device, mailbox | Sessions here manage message encryption across asynchronous, multi-device communication. | [Matrix client-server v1.16](https://spec.matrix.org/v1.16/client-server-api/): room, state, timeline, ephemeral event | Room sync distinguishes retained timeline/state updates from ephemeral events and per-user data. | Useful distinctions for a messaging Resource's contract. “Room” should remain a possible application capability, not a sixth family or the definition of every Conduit. | [Envoy terminology](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/intro/terminology): upstream/downstream, listener, cluster, host | These names are relative to the proxy and its networking responsibilities; a host can be a logical application rather than a machine. | Prefer role-qualified endpoints. “Host,” “source,” “upstream” and “provider” require a stated viewpoint. ## Cross-system conclusions

There is no canonical vocabulary covering all of Conduit. The strongest agreement is at narrower
boundaries: packages distribute, contracts define, operations are invoked, inputs and outputs carry
values. Words become less portable as they approach lifecycle or authority. “Resource,” “session,”
“runtime,” “flow,” “requirement” and “binding” are especially dependent on context.

The theme works when it reinforces an actual relationship: endpoints connect through a Conduit;
requests follow a route; filters narrow flow. It becomes misleading when a valve supposedly represents
all distributed enforcement, a stream implies ordering that is absent, or a pump implies autonomous
work. The [candidate analysis](CANDIDATES.md) applies these lessons without importing another system's
semantics.
