## The decisions it applies

1. **Where they live.** S7's is `experiments/018-s7-outside-package/README.md`, S8's is
   `experiments/019-s8-filtered-search/README.md` and S10's is
   `experiments/021-s10-swapped-providers/README.md`. Each holds a placeholder now: replace it.
   The scenario's dated results go beside it later. The index rows in `experiments/README.md`
   and the links from ROADMAP.md's table of scenarios are already in place; change neither. A
   scenario's row in that table is its row in the register, so add no register row.
2. **The form.** Every pre-registration of orders 101 to 103 has the same sections, so that the
   owner can take them together.
   - It opens with a box, "For the owner", with one line for each item labelled *proposed* and
     one for each open question.
   - Keep each README under about 250 lines.
   - A question shared with another scenario, such as which accounts sign in, is asked in the
     same words in each README; the coordinator gathers them.

   Then come these sections, in this order:
   1. *Status*: "Pre-registered on DATE by work order 103. Awaits the owner's acceptance of
      what it proposes; nothing here runs before that. Ruling 45 fixes what an experiment must
      show before it runs, and IN_FORCE.md topic 13 lists the criteria the owner has accepted.
      No result is recorded here."
   2. *Question*: what the scenario settles, from its row of the roadmap.
   3. *What it must show*, as numbered pass conditions, each an observation with the way it is
      judged.
   4. *What it covers*: the cases and measurements of round 6 that the roadmap names for it;
      the promise IDs it exercises, by file, as `spec/` states them today; and the register
      items it feeds or overlaps.
   5. *The tasks*: numbered `S7-T1`, `S7-T2` and so on, each saying what the author does, in
      the form of the first build's T1 to T7. A fault the run injects is preparation, said
      apart from the author's tasks.
   6. *Measures*: decision 4, then each measure of its own, with how it is counted.
   7. *Vectors expected*: each proposed vector by a proposed name, with the promises it cites
      and whether it is a safety vector. A safety vector is one whose failure would be unsafe
      as [the tracker](../AUDIT.md) defines it (search for "mark as unsafe"), and it names the
      safety promise it tests. Name any vector under `conformance/` that already covers a case.
   8. *Runs*: who authors; which Agents and clients; the machines, accounts, services and
      provider packages each run needs; the owner's presence and time; how many runs; and what
      is recorded.
   9. *What it needs first*: the engine, specification and package work that must exist, by
      function and promise, and what the owner must set up.
   10. *What `spec/` does not yet decide*: each behavior the scenario needs that no promise
       states. Cite the IN_FORCE.md line marked *spec pending* where there is one.
   11. *Open for the owner*: each question with its options and a recommendation, marked as a
       recommendation.
   12. *Limits*: what the scenario does not show.

   Every pass condition, measure, counting rule and vector carries one of three labels:
   *ruled*, with its source; *accepted by the owner*, with its source; or *proposed, for the
   owner's acceptance*.
3. **Pass conditions.** Each scenario has ruling 47's: it runs end to end on the reference
   engine with its vectors passing, and every safety vector it adds passes.
   - **S10, ruled.** Each provider contract it swaps has two implementations, on different
     existing tools, that pass the same vectors (ruling 40; IN_FORCE.md topic 13; A63).
   - **S7, accepted by the owner, but not a condition of v0.** "The check of package authoring
     includes an implementation not written in Rust (S7)" (IN_FORCE.md topic 14). It is a
     check for publication that builds on S7 (ruling 47's actions after a decision to publish).
   - **Where that implementation lives** is a question for the owner. The repository's code is
     Rust, with only the Python checkers excepted (AGENTS.md; IN_FORCE.md topic 13).

   Every other criterion is proposed.
4. **Measures (the lane coordinator's decision, logged for the owner to strike).** The first
   build's measures were written for S1. They apply to every scenario's author runs as
   follows.
   - **Carried over**, cited by link and not restated:
     - the table of measures;
     - three of its counting rules: provider work apart; a client's concepts count; requests
       and intervals without access;
     - ruling 63's count of lines, with the panel's actions listed apart (ruling 68, R1);
     - IN_FORCE.md topic 13's rules for each run.
   - **Not carried, because they are S1's alone**:
     - the comparison with A70 and its bar (ruling 71, point 3);
     - the rules for T3's reach around Conduit and for T4 and T5 against the better baseline;
     - S1's local name `project`.

   No scenario here has a numeric bar, and observed time and mistakes are recorded before any
   target is set (ruling 46, point 3). A scenario may propose a comparison, labelled proposed.
   - **D01 and D09 belong to order 101.** It defines them in S2's pre-registration,
     `experiments/013-s2-shared-login/README.md`, which is written at the same time as this
     order. Cite that file and the measurement by name, and do not define them again. S7 uses
     D01 for the outside author's package, and S10 repeats D09 on the swapped store.
   - **D15** is defined here, for each provider.
   - **D16** asks that S10's comparison be defined before it runs, and this pre-registration
     defines it in full: the provider-specific edits it counts, the replacements it allows, and
     what a swap must keep.
   - **S2's tasks.** S10's replay of S2 uses S2's tasks as order 101 writes them. Refer to them
     by that file's section "The tasks", and do not restate them.
5. **Who authors S7.** S7's author is an outside author: a fresh session that has the
   specification, the package format and contracts, and the CLI's format reference, and none
   of this repository's history, as the fresh author of increment 4 had (IN_FORCE.md, topic
   13). Whether it is a Codex or a Claude session, and in which language the implementation
   that is not in Rust is written, are proposed for the owner.
   - **The package** is an existing MCP server whose command repeats a named argument, such
     as `-e`, as round 6's decisions require (MAN-010). Binding one occurrence of such an
     argument is *open* (IN_FORCE.md topic 11).
   - **Candidates.** Propose candidates that today's runner can start: npm packages, over
     stdio (DL16). Flag any candidate that needs more, such as Docker, as a dependency.
     You have no network, so mark every candidate unverified and say how each was chosen.
6. **S10's providers.** For each provider contract S10 swaps, name the first implementation and
   the second, on a different existing tool, from A63's candidates in docs/AUDIT.md:
   - **secrets**: the first is S2's store, the macOS keychain (ruling 46, point 5). The second
     is 1Password, after A73 under experiment 005's safety rules and the owner's approval for
     its desktop-app case, or the file store that ships with the engine;
   - **runtime**: a local process, then Docker;
   - **package source**: a local directory, then Git.

   The machines contract's second implementation is S3's, not S10's. Where a choice is open,
   give options and a recommendation.

   **Accounts.** S10's replays of S1 and S2 use second subscription accounts that the owner
   provides. Each is signed in through Conduit's own sign-in flow (ruling 49), so the replays
   also test Conduit's authentication. No API key is used (ruling 72, point 2). Say which
   replay needs which account.
7. **No new language.** A behavior a scenario needs that `spec/` does not state is a finding of
   class gap in your report, and a line of section 10. No promise is drafted, and no task
   assumes an answer. This covers S8's filtering of returned and derived content, and the

   DL16), wherever `spec/` leaves them open.
