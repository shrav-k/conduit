What the counts show, in short:

- Setting S1 up (T1, T2) wrote 49 lines in 7 files and needed 13 concepts. The three mistakes
  made during T1 were about trust and approval, not about access. Until the project is
  trusted, Claude Code ignores its project's `allow` rules and Codex its whole project file;
  the realistic way to trust it is a dialog that writes the user's home file. Codex refuses an
  MCP write until an approval setting allows it.

  The values that must agree, such as the directory's path, the server's definition and the
  history's convention, are written once per agent.

  its restriction was a list of tool names. The check found it; two manual steps restored
  the intended access, and a running interactive B session would also need a restart, which
  was not tested.
- Revoking one agent's access (T7) was one rule in one file. It left the other agent working,
  and it reached the revoked agent's running session at its next turn.

## How each measure was counted

The definitions are those of [the measures](../../docs/implementation/FIRST_BUILD.md#measures),
unchanged. Where a definition left a choice, this run chose as follows.

- **Lines written**: each non-blank line added, changed or removed, counted once in a task even
  where it was edited more than once; the number of edits is given in brackets where it
  differs. A removed line is counted as a line changed. There are no comments in the files.
- **Concepts met**: each tool's own concepts, numbered in the order first needed (C1 to C22
  below). C14 and C15 are the author's own design, not a tool's concept, and are listed but
  not counted. Harness flags are not counted.
- **Grants made by hand**: an MCP server entry, an `allow` rule and a Codex approval setting
  each give one agent access to one thing. A `deny` rule, `disabled_tools` and the server's
  `--read-only` take access away and are not grants.
- **Duplicated configuration**: each distinct value written in more than one place, counted on
  the files as they stand at the end of the task.
- **Per-agent changes of access**: the files edited to change, or in T1 and T2 to set, what each
  agent can reach. Restarts are listed apart.
- **Provider-specific code**: each line in the author's files that names the backing tool:
  `npx`, the server's package, or a tool name that only this server defines (such as
  `write_file`). Counted on the files at the end of the task. The agents' own keys, such as
  `sandbox_mode`, are agent-specific, not provider-specific, and are not counted.
- **Recovery steps that need a person**: each manual action taken after a failure that a check
  showed, to reach the intended state. Each realistic step is counted once, even where the lab
  needed a stand-in for it. A step that rests on behaviour this run did not observe is listed
  apart, as expected.
- **Observed time**: from the log's start line of the task to its end line, checks included.

Evidence: the author's [timestamped log](evidence-2026-11-09/log.txt), the
[prompts](evidence-2026-11-09/prompts.txt) and one trimmed output per run in

### T4: a live change, A may also write, B may only read

Edits:

  changed, 7).

The live part. One A session was kept running on a stream-json input
([t4-a-live](evidence-2026-11-09/t4-a-live.txt)). Before the edit it had no write tool. After
the edit, in the same session, it found none either: "No matching deferred tools found", and
its tool list stayed at 10 `project` tools. A retest after T7, with a 10-second pause after the
edit, gave the same result ([verify-t4-live](evidence-2026-11-09/verify-t4-live.txt)): in
this setup, removing the tool-level deny rules did not reach the running session. A new
session had all 14 tools and wrote `shared/t4-a.txt` ([t4-a-1](evidence-2026-11-09/t4-a-1.txt)).
B, in its next run, was offered only the 10 read tools ([t4-b-1](evidence-2026-11-09/t4-b-1.txt)).
Codex reads its configuration when its process starts. `codex exec` takes one prompt per
process, so B had no running session to change; an interactive Codex session was not tried.

What this does not show (audit): every A run loaded `settings.json` twice, as the untrusted
project file, whose deny rules apply and whose allow rules are ignored (each run's stderr says
so), and as the `--settings` file that stood in for trust. The deny rules removed in T4 were
in both layers when the session started; the deny added in T7 was in neither when its session
started. The observations of T4 and T7 therefore fit two causes that this run does not
separate: that Claude Code does not drop a tool-level deny from a running session while it
does apply a server-level one, as the author concluded; or that it reads the `--settings` file
only at start, so a deny that was there at start stays. The retest kept the same design. A
test that separates them, such as removing a server-level deny that was present at start, was
not run. Whether a trusted workspace, with no `--settings`, needs this restart is therefore
open.

Concepts met: C18, Codex's `disabled_tools`; C19, a running Claude Code session, as set up
here, keeps its tool list when a tool-level deny is removed (see the paragraph above for what
this does not show).

Recovery steps: restart A's running session (1). It was needed in the setup as run, with the
`--settings` stand-in; whether it is needed with a trusted workspace is open (above).

## What surprised the author

1. **Trust gates both agents' project configuration, and lives in the home directory.** Claude
   Code applies a project's deny rules before trust but not its allow rules. Codex loads
   nothing of a project's file until trusted. In both, the trust is written by a dialog into
   the user's global file. A per-project setup is therefore not self-contained.
2. **A malformed override fails silently.** Codex took `projects."<path>".trust_level` without
   a warning and trusted nothing. It took the same key without quotes, or as an inline table.
3. **An upgrade widened access.** Restrictions written as lists of tool names, in both agents'
   syntaxes, let through the write tools that 2.2.0 added. The server's own `--read-only`, new
   in that version, is the restriction that does not depend on tool names.
4. **Live changes in Claude Code looked asymmetric.** A deny on a whole server, added while a
   session ran, reached it, and so did its removal. Removing denies on single tools that were
   there when the session started did not, so the agent that gained access was restarted. With
   the `--settings` stand-in for trust, this run cannot tell whether the cause is the kind of
   rule or the fact that the `--settings` file is read only at start (T4).
5. **The servers' limits bound only the MCP route.** Codex's read-only sandbox lets its shell
   read any file the user can, A's configuration included. Codex also offers B MCP servers
   tied to the ChatGPT account that no file of the setup declares (T3, found by the audit).
   Claude Code's built-in tools ask, and an interactive person can say yes. A's revoked server
   kept running.
6. **The reference server's Roots.** The 2.x README warns that a Roots-capable 2025-era client
   replaces the command-line directories. Neither client did here, but nothing in the files
   says whether one will.
7. **Evidence from Codex is incomplete.** Commands that Codex runs through its code-mode tool
   leave no event in `--json`, so its report of a shell result had to be confirmed with
   `codex sandbox`.

## Limits

The limits stated before the run:

- The author is an AI agent that knows Conduit's design, and the same author does the build's
  tasks. Neither result stands for a newcomer's effort.
- One run of each task, on one machine. The counts are exact; the times are observations.
- Codex was not installed at pre-registration. It was installed and signed in on 2026-11-09,
  before the run, and both agents were used.

New limits:

1. **Headless only.** Each interactive prompt was replaced: the trust dialogs by files and
   flags (counted as 9 lines), the approval of the project's MCP servers by `--mcp-config` (not
   counted; that prompt was not observed in this run), permission prompts by refusals. An
   interactive author would click instead, and could approve what the files do not allow.
2. **Isolation, not a clean machine.** The owner's own settings, MCP servers and Codex
   configuration were kept out by flags, not removed. A person's ordinary setup would mix with
   them, and T3's inspection would grow by the 5 files listed there.
3. **Live changes were tested on Claude Code only.** `codex exec` runs one prompt per process.
   Whether an interactive Codex session picks up a change was not tested.
4. **The author read the server's README for 2.1.0 and 2.2.0 in step 1**, before T1, and so
   knew of Roots, `--read-only` and the new write tools. T5's minimal upgrade was made
   deliberately, to observe it.
5. **Node 21.5.0 is below the `node >=24` that 2.x declares.** Both versions ran, but the
   server's authors do not promise it.
6. **The models were chosen for short runs**: `--model sonnet` for A and low reasoning effort
   for B. The access results do not depend on the model; the agents' behaviour, such as A's
   misnamed post, may.
7. **The stand-in for Claude Code's trust adds a settings layer.** A's settings were loaded
