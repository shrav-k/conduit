## What the sources say

### 1. What authorizes a read

**The service account.** “Each service account has a service account token that you can provide
as an environment variable for authentication.” (SA2)
“When creating a service account, you choose the vaults it can access and its level of access.
The service account only returns information from vaults it can access.” (SA5)
“A service account can only read items from vaults it has READ access to.” (SA5)

“You can't grant a service account access to your built-in Personal, Private, or Employee
vault, or your default Shared vault.” (SA2)
“Service account permissions, vault access, and Environment access are immutable.” (SA2)
“You can’t grant a service account access to vaults that have service accounts turned off,
even if the creator of the service account has permissions to manage the vault.” (SA5)

As a summary, SA5 also limits grants to vaults the creator reaches and says disabling service
accounts for a vault removes existing access. OP1 names read and item commands; it says to
specify a vault when the service account has more than one, for item/document commands.
The documentation describes vault permissions, not a separate item-by-item grant list.

**The desktop app's integration with 1Password CLI.** “Integrating 1Password CLI with the
1Password app allows you to use accounts you’ve added to the 1Password desktop app with
1Password CLI.” (DA2, HTML)
“The user must confirm the prompt for 1Password CLI to be granted access to the requested
account details.” (DA2)
“Authorization in 1Password CLI occurs on a per-account basis. If you sign in to multiple
accounts, each account must be authorized separately.” (DA2)

As a summary, this authorizes access to an account already in the app. The pages read say
nothing on this: a separate CLI authorization grant restricting individual vaults or items
within that account.

OP4 explicitly adds SDKs under this desktop route: “1Password SDKs allow you to build
integrations between 1Password and other local applications and scripts that authenticate
using authorization prompts from the 1Password desktop app on the user’s device.” (OP4)
OP4 says authorization is per account and process, and its prompt describes scope and duration.
It does not supply a vault/item permission table for local integration grants.

### 2. Whether a prompt can appear

**The service account.** “1Password Service Accounts give scripts, CI/CD pipelines, and servers
scoped access to secrets in 1Password, without a person signing in.” (SA1)
“A service account is a type of user account that’s meant for programmatic access. Service
accounts differ from regular 1Password accounts in that you don’t need to provide an email or
an account password.” (SA5)

As a summary, these pages describe token-based programmatic reads without a person signing
in; they do not describe a per-read biometric, password or approval prompt or an approval
session's idle/absolute lifetime. Creating and managing a service account is separately
documented with a person's sign-in (SA2/SA3); those setup acts are not a read observation.

**The desktop app's integration with 1Password CLI.** “Every time you use 1Password CLI in a
new terminal window or tab, you'll be asked to authorize with biometrics.” (DA2)
“This authorization establishes a 10-minute session that automatically refreshes on each use.”
(DA2)
“Authorization expires after 10 minutes of inactivity in the terminal session. There's a hard
limit of 12 hours, after which you must reauthorize.” (DA2)

“If biometrics are not available a prompt confirming the user's device password is used
instead.” (DA2) As a summary, DA2 names macOS TouchID/Apple Watch or device password, Linux
PolKit with fingerprint/OS password, and Windows Hello with fingerprint, face or OS password.
DA1 also documents an OS data-access approval when macOS blocks terminal access to app data.
These are documented prompt conditions, not observed prompts.

Under the heading “Accepted risks”, DA2 says: “A user or application with root/administrator
level privileges on the same system may be able to circumvent one or more security measures and
could obtain access to 1Password accounts through 1Password CLI without authorization if (and
only if) the 1Password app is unlocked.” (DA2) “Applications that are granted accessibility
permissions on macOS may be able to circumvent the authorization prompt.” (DA2) Under the same
heading, OP4 says: “A user or application with root or administrator-level privileges on the
same system may be able to circumvent one or more security measures and could obtain access to
1Password accounts.” (OP4) As a summary, DA2 and OP4 list these as accepted risks, not as a
documented way to read.

For the SDK desktop integration: “Users must approve the request using the same method they
use to unlock their 1Password app, like with biometrics or their 1Password account password.”
(OP4) “Authorization expires after ten minutes of inactivity, after which the user must
re-authorize.” (OP4) OP4 also expires authorization on locking the account; no absolute SDK
session maximum was stated in the parts read. DA2's 12-hour CLI maximum is not assigned to SDKs
by this note.

### 3. Locked, closed or absent

**The service account.** SA2 describes the token giving access “without a person signing in
and without running any extra services.” (SA2) OP1's requirements are signing up for 1Password,
installing its CLI (2.18.0 or later), and creating a service account. OP3's SDK tutorial lists
“(Optional) 1Password desktop app.” (OP3)

As a summary, the documented service-account route uses a token, with no desktop app or
person's desktop session listed as a runtime prerequisite. These pages do not describe its
behavior separately for a locked, quit or absent app, SSH, or a background service. They name
scripts, CI/CD pipelines and servers (SA1/SA2), rather than an app-session dependency.

**The desktop app's integration with 1Password CLI.** “Authorizing use of 1Password CLI while
the 1Password app is locked will result in the 1Password app unlocking. When the 1Password app
is locked, all prior authorization is revoked. Any new invocation of 1Password CLI will require
new authorization. If a process is running at the moment authorization is revoked or expires,
it will be able to finish its task and exit.” (DA2)

Whether a read can succeed while the app remains locked: **it does not say**. DA2 says prior
authorization is revoked, a new invocation needs authorization, and authorizing unlocks the
app; its final sentence says an already-running process may finish its task. It does not
identify that task as a read or specify the outcome of an in-flight read after locking. This
note therefore records both the new-invocation rule and the in-flight qualification, without
claiming a demonstrated locked-app read for FR-487's stage 2 condition.

DA1 lists a 1Password subscription and the corresponding desktop app as requirements (and a
running PolKit authentication agent on Linux). DA2 says: “1Password CLI uses inter-process
communication to reach out to the 1Password app to obtain access to the accounts stored in the
app.” (DA2) For connection errors, DA1 says: “Restart the 1Password desktop app, then run your
1Password CLI command again.” (DA1)

As a summary, the pages require the app and describe keeping it in the menu bar, notification
area or system tray; closing a window is not described as quitting it. They do not specify an
exact outcome for a quit/uninstalled app, or a process started over SSH or by a background
service with no person logged in to the desktop. The pages read do not say whether DA2's or
OP4's accepted risks (question 2) apply when no person is logged in to the desktop. DA1's local
WSL restriction is not an SSH result.

For SDKs: “If the account in the 1Password app is locked, all existing SDK authorizations are
immediately revoked.” (OP4) OP4 describes local IPC and user approval, without an in-flight
completion qualification like DA2's. It does not state an SSH/background-service outcome.

### 4. Rate limits

**The service account.** “Service account tokens have hourly limits applied to both read and
write actions independently. The 60-minute time window begins after 1Password receives the
first request.” (SA4)
“Daily limits determine the total number of requests that all service accounts within a
1Password account can make in a 24-hour window.” (SA4)

This table summarizes SA4's tables; the numbers are documentation, not measured limits:

| Account type | Reads per 60 minutes, per token | Writes per 60 minutes, per token | Read/write requests per 24 hours, all service accounts in the account |
| --- | --- | --- | --- |
| 1Password Business | 10,000 | 1,000 | 50,000 |
| 1Password Teams | 1,000 | 100 | 5,000 |
| 1Password / 1Password Families | 1,000 | 100 | 1,000 |

The documented hourly response is: “Error: [ERROR] (429) Too Many Requests: You've reached the
maximum number of this type of requests this service account is allowed to make. Please retry
in 59 minutes or try other requests.” (SA4)
The daily response is: “Error: [ERROR] (429) Too Many Requests: You've reached the maximum
number of this type of requests this 1Password account is allowed to make. Please retry in
23 hours and 59 minutes or try other requests.” (SA4)
These are SA4's example wait times, not a fixed backoff inferred for every caller. No numeric
process exit status is stated there.

“1Password CLI commands make one request unless otherwise noted.” (OP1)
As a summary, OP1 lists both item get and read as three reads, reduced to one by passing item
and vault IDs. Its other examples include list, create, delete, edit and vault commands with
multiple requests. Commands and rate-counted requests are not counted as interchangeable here.

**The desktop app's integration with 1Password CLI.** The pages read say nothing on this:
plan/period/request rate limits or the response past a desktop CLI or local SDK rate limit.
SA4 labels its limits service-account limits; this note does not transfer them to the desktop
route. No named page for this note was unreadable.

### 5. The token

**The service account.** “Save the token in 1Password immediately to avoid losing it. Treat
this token like a password, and don't store it in plaintext.” (SA2)
“Set the OP_SERVICE_ACCOUNT_TOKEN environment variable to the service account token” (OP1).
The documentation says the creation wizard/CLI returns the token only once (SA2).
“The steps to create the token happen on your device (client-side); nothing sensitive goes to
1Password’s servers. It’s up to you to save and protect the service account token.” (SA5)

“You can set an expiry to a service account using the --expires-in flag.” (OP2)
As a summary, OP2 gives seconds, minutes, hours, days and weeks as duration units; SA2 gives a
24-hour example. No default token lifetime or universal maximum was stated in the parts read.

“Rotating a service account token generates a new token with the same permissions. You can
also specify an expiration for the current token, so you have time to update to the new token
without any interruption in service.” (SA3)
As a summary, SA3 directs rotation/revocation on the service account overview; examples for
expiring the old token are now, one hour and three days. It directs saving the replacement in
1Password. If the sign-in address changes, SA3 says tokens redirect for 30 days and directs
rotation. That is not stated as the token's ordinary lifetime.

“Revoking a service account token immediately removes its access to 1Password vaults.” (SA3)
“A service account token associated with a deleted service account can’t authenticate.” (SA5)
The pages read say nothing on this: exact response bodies or exit statuses for revoked or
expired tokens. OP2 documents expiry, without specifying its error. File-based passing is
FR-487's future run rule, not a storage method attributed to these vendor passages.

**The desktop app's integration with 1Password CLI.** “Session credentials are used to
identify the terminal window or application where 1Password CLI is invoked.” (DA2)
“These credentials don't consist of any sensitive or secret information.” (DA2)

As a summary, DA2 derives the macOS/Linux session identity from tty and start time, and the
Windows identity from the invoking process's PID and start time. The app holds the accounts,
and CLI requests access over IPC. The parts read do not specify a persistent CLI session-token
file, its storage location or a token-rotation mechanism for this route. DA1 distinguishes
previously manually added CLI account details from accounts in the app, and documents removing
the former without affecting the latter. Question 2 gives authorization lifetimes and question
3 gives revocation on lock.

For local SDKs: “The credential used to authenticate never leaves the 1Password app process.”
(OP4) OP4 describes per-process authorization in the app and local IPC; no separate persistent
SDK credential file or default storage path is stated.

### 6. Errors

**The service account.** “A service account token associated with a deleted service account
can’t authenticate.” (SA5) “Revoking a service account token immediately removes its access to
1Password vaults.” (SA3)
These are consequences documented by the sources, not error strings. The pages read say
nothing on this: specific error messages, HTTP statuses or numeric CLI exit statuses for a
revoked token, an expired token, a missing item or no network. Nor do they assign a
locked-desktop-app error to this route. SA4's 429 examples concern limits only, as question 4
records. Stage 2 would measure errors; no value was observed here.

**The desktop app's integration with 1Password CLI.** DA1 names “LostConnectionToApp”,
“connectionreset” and “No accounts configured for use with 1Password CLI” (DA1), with instructions
to enable integration, open/unlock the app, keep it in the appropriate tray/menu and restart.
DA1 also describes a macOS data-access permission case for the no-accounts message. It does
not map these messages one-to-one to app lock, quit, absence or no network.

DA2 says a new invocation after locking “will require new authorization.” (DA2) That is a
prompt condition, not a documented locked-app error code. The pages read say nothing on this:
exact errors or numeric exit statuses for a locked app, a revoked/expired desktop credential,
a missing item or no network, including the local SDK route. No named page was unreadable.

### 7. Plans and accounts

**The service account.** SA2's requirements include “Sign up for 1Password.” and “Have adequate
account permissions to create service accounts.” (SA2)
“By default, only owners and administrators can create and manage service accounts in
1Password Teams and 1Password Business.” (SA3)
As a summary, SA3 documents delegating creation to groups/people, their management of their own
service accounts, and vault grants requiring Allow Managing in Teams or Manage Vault in
Business. SA4 lists limits for 1Password, Families, Teams and Business; OP3 lists a 1Password
subscription. These passages do not provide a separate Enterprise entitlement or a free/trial
entitlement statement. No owner's plan was checked.

**The desktop app's integration with 1Password CLI.** DA1 lists “1Password subscription”
(DA1), together with the OS's desktop app. As a summary, it specifies Mac, Windows or Linux;
Linux also needs PolKit and a running authentication agent. DA2 describes accounts added to
the app and separate authorization for each. The pages read say nothing on this: a further
CLI plan-by-plan entitlement matrix. OP4 gives no separate SDK subscription-plan matrix.

### FR-487's expectation

[FR-487](https://github.com/shrav-k/conduit/blob/077fa47ecd4d2172d4f9204c6fcbf0f43a4e2b9d/docs/proposals/full-review/findings/G3-native-probes.md#fr-487) marked its
expectation as to be checked and not a result. The documentation bears on its three parts as
follows:

- **A service account is built for unattended reads with a token: supported.** SA1 says
  “without a person signing in” (SA1); SA2 says each service account has a token supplied for
  authentication, quoted in question 1. This is documentation support, not an observed read.
- **The desktop integration needs the person to authorize: supported, subject to the accepted
  risks DA2 and OP4 list (question 2).** “The user must confirm the prompt for 1Password CLI to
  be granted access to the requested account details.” (DA2) OP4 likewise requires explicit
  approval for SDK local integrations.
- **It stops when the app locks: supported for prior authorization and new invocations;
  contradicted as an unqualified claim about all work stopping.** “When the 1Password app is
  locked, all prior authorization is revoked. Any new invocation of 1Password CLI will require
  new authorization.” (DA2) But: “If a process is running at the moment authorization is revoked
  or expires, it will be able to finish its task and exit.” (DA2) OP4 says all existing SDK
  authorizations are immediately revoked on lock; it does not discuss that CLI qualification.

### Other routes

SA1's comparison names two other routes for automated workflows, recorded here without
examining their pages:

  API you deploy in your own infrastructure” (SA1).

  all — access is verified per run using your CI/CD platform’s OIDC identity” (SA1).

OP3's SDK with a service-account token is the service-account route; OP4's local SDK integration
is recorded under the desktop route above, rather than treated as an unattended alternative.
