# 027 — A5 stage 1, before step 1, 2026-11-19: the refresh-blocked probe

Every result of this experiment is obtained under one operating-system user, so none shows Agents
kept apart (ruling 75 B3). This probe ran Codex 0.167.1's `codex app-server` on the Linux node,
inside a network namespace that held loopback alone, against a fabricated login in a scratch home
and plain-http stubs on loopback, on 2026-11-19, under work order 208, as
[its pre-registration](README.md#stage-1-before-step-1-the-refresh-blocked-probe) sets it. No real
account, login or token was used, and nothing reached OpenAI. It shows what that binary did on
that machine with that login, and nothing of the Mac's binary, of OpenAI's service or of any other
version. It states outcomes, and decides nothing for order 050m.

## The source the probe relied on

### 1. The file store

In this reading, the home's auth.json holds an optional `auth_mode: AuthMode`, `OPENAI_API_KEY:
String`, `tokens: TokenData`, and `last_refresh: DateTime<Utc>` alongside optional `agent_identity:
AgentIdentityStorage`, `personal_access_token: String`, `bedrock_api_key: BedrockApiKeyAuth`, and
`bedrock_access_keys: BedrockAccessKeysAuth` (`login/src/auth/storage.rs:51-77`), and a ChatGPT
login selects the ChatGPT mode (`login/src/auth/manager.rs:460-467`).

`TokenData` has `id_token: IdTokenInfo`, `access_token: String`, `refresh_token: String`,
`oauth_provenance: Option<AccountOAuthProvenance>`, `login_owner_id: Option<String>`, and
`account_id: Option<String>`. The provenance holds `issuer: String` and `client_id: String`. Serde
reads and writes the ID token as the JWT string, using the parsed claims in memory
(`login/src/token_data.rs:10-40`, `login/src/token_data.rs:215-228`).

### 2. The claims and proactive refresh

In this reading, the ID-token parser takes a top-level email or falls back to the profile email, and
takes the plan, user ID and account ID from the nested auth claim (`login/src/token_data.rs:86-119`,
`login/src/token_data.rs:144-154`, `login/src/token_data.rs:189-213`).

The payload decoder reads base64url without padding and checks for a nonempty third segment. The
access token's `exp` is seconds since the Unix epoch and keeps the five-minute window test
independent of the ID-token claims (`login/src/token_data.rs:144-162`,
`login/src/auth/manager.rs:222`, `login/src/auth/manager.rs:3528-3546`).

### 3. The refresh request and response

In this reading, refresh posts JSON with `grant_type`, `client_id`, `refresh_token` and
`refresh_reason`, and on success decodes optional new ID, access and refresh strings
(`login/src/auth/manager.rs:1774-1799`, `login/src/oauth/client.rs:97-149`,
`login/src/auth/manager.rs:1855-1860`).

```rust
struct RefreshResponse {
    id_token: Option<String>,
    access_token: Option<String>,
    refresh_token: Option<String>,
}
```

Endpoint selection prefers the override, then the stored issuer with the token path appended, then
the default endpoint. The load and refresh both call that selector
(`login/src/auth/manager.rs:435-453`, `login/src/auth/manager.rs:1872-1878`,
`login/src/auth/manager.rs:3612-3643`). The write lock is taken inside persistence after the
exchange returns successfully (`login/src/auth/manager.rs:3629-3657`,
`login/src/auth/manager.rs:1725-1735`).

### 4. The issuer's scheme

In this reading, the file load carries the stored issuer through endpoint selection and the refresh
posts to the selected endpoint, with no refusal of a loopback HTTP issuer in the paths read
(`login/src/token_data.rs:24-40`, `login/src/auth/manager.rs:435-453`,
`login/src/auth/manager.rs:1872-1878`, `login/src/auth/default_client.rs:449-459`,
`login/src/outbound_proxy.rs:39-44`, `login/src/oauth/client.rs:115-139`).

### 5. Workspace discovery

In this reading, with a base ending in `/backend-api` the request is `GET
/backend-api/wham/accounts/check` and takes the access token in the Authorization bearer header
(`backend-client/src/client.rs:150-156`, `backend-client/src/client.rs:251-259`,
`backend-client/src/client.rs:294-306`, `backend-client/src/client.rs:424-434`,
`model-provider/src/auth.rs:114-129`, `model-provider/src/auth.rs:411-427`).

The fixture returns an `accounts` array with the account's `id`, `workspace_backend_origin` and
`account_routing_override`. Routing accepts the `NO_CONSTRAINT` override and requires an HTTPS
origin for the supplied backend, with no path beyond the root, query, fragment or user information
(`backend-client/src/types.rs:129-155`, `app-server/tests/common/auth_fixtures.rs:18-35`,
`app-server/src/request_processors/account_processor/workspace_routing.rs:563-617`).

### 6. A 401 after recovery

In this reading, the unauthorized result after recovery with no new credential generation, unless
the stored refresh rejection branch applies, reports “workspace routing discovery unauthorized
(401)” (`app-server/src/request_processors/account_processor/workspace_routing.rs:76-77`,
`app-server/src/request_processors/account_processor/workspace_routing.rs:411-452`).
