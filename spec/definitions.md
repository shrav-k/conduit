# Definitions

Draft. These are the terms the promises rely on, each with one meaning. The promises govern:
where a row names a promise, that promise states the rule and the row only says what the word
means. The first table gives the core terms in one line each; the section it links holds the
full row of each. The decision records and their reasons are listed in
[Where the reasons are](README.md#where-the-reasons-are).

`serving` and `unreconciled` are working names.

## Objects and documents

| Term | Meaning |
| --- | --- |
| family | One of the six families: Interface, Agent, Resource, Pool, Fleet and Conduit. The first five have rows here, and Conduit under [Relationships](#relationships). |
| Interface | One of the six families: where a person, or a system outside, acts on the system. An Interface is an actor: it makes requests on its own behalf (IFC-021). It has no placement (PLC-006), and can be the consumer or the target of a Conduit (OBJ-013). It is also the control panel for pending actions (PND-002). |
| Agent | One of the six families: a participant whose model decides its own actions. An Agent is an actor, as an Interface is, has exactly one placement (PLC-001), and may name the runtime provider that runs it (PRV-006). A turn of its model is model work. It has exactly one owner, a Fleet, fixed for its life (FLEET-002). Setting it up, retiring it, inspecting it and reconciling its invocations go through its Fleet (ACC-033). |
| Resource | One of the six families: a shared thing that instances use. A Pool owns it: a Resource has exactly one owner, which is a Pool (POOL-001), and exactly one placement (PLC-001), and it may name the runtime provider that runs it (PRV-006). It is not an actor: it makes a request only to serve an invocation it received (IFC-021). A provider is a Resource (PRV-001). It is not a resource of the Model Context Protocol, which a result may carry as a resource link or an embedded resource; a Resource template is not an MCP resource template. |
| Pool | One of the six families: what owns and groups Resources. Its template may declare entries (POOL-002). It has no placement, can be the target of a Conduit, and is never a consumer or a caller (OBJ-013, ACC-028). |
| Fleet | One of the six families: what owns Agents, as a Pool owns Resources (FLEET-002). Ownership permits nothing; administering an Agent goes through its Fleet, and running its turns takes a Conduit to the Agent (FLEET-004, ACC-033). A Fleet runs nothing and applies nothing to its Agents together: they are never configured, upgraded or started as one, and it holds no count of copies. It is engine-local, has no placement, contains no Pool and is not a group of machines; a machine is represented by a node. It is never a caller. An Agent never changes Fleet (FLEET-002). |
| frame, framed document | The explicit document form with `apiVersion`, `kind`, `metadata` and, for a template or contract, `spec`; a framed instance uses `from` and its family's standard arguments instead of `spec`, and may omit `metadata` (OBJ-012, OBJ-013, OBJ-020). |
| sectioned document | A documents-file map without `kind`, holding named sections and optional `apiVersion`, translated into canonical framed documents by SCT-001 to SCT-016. Its effective version is explicit or inherited from the manifest (SCT-002). The manifest and contracts retain their own forms; the wire and store remain canonical. |
| section | One of `templates`, `interfaces`, `agents`, `resources`, `pools` and `conduits` in a sectioned document. Family maps under `templates` hold templates; other sections hold definitions of the named family (SCT-005, SCT-006, SCT-016). `fleet` is a per-file key, rather than a map section. |
| sectioned definition | A named member of an instance section. Inline it states `type` (or `capability` for a Conduit) and makes a template and its instance together; referenced it states `from` and makes only the instance (SCT-006, SCT-016). A Pool's entry remains a nested instantiation, a different term. |
| translation | The fixed, pure expansion of sectioned documents into framed documents. It depends on the authored text and effective version, with file boundaries only for `fleet`, and reads no package, stored object or environment (SCT-003, SCT-004). SCT-014 maps rejecting diagnostics back to the authored text. |
| generated name | A name computed rather than written. The short form joins authored keys by the fixed SCT-013 rules, for example `worker--files--t`, and rejects one longer than 63 characters. An unnamed canonical instance instead receives a name under OBJ-003 and DL15. |
| `consumes` | An Interface, Agent or Resource definition's map of local names to Conduits it consumes. Each item makes a standalone Conduit to its explicit `to`, using a template or an inline capability and operation list (SCT-007, SCT-008). |
| `operator` | A short-form key making root's Conduit to an Interface, Agent or Resource, with that definition's name as its local name (SCT-009). A Pool accepts no such key. The ordinary prose word for whoever runs the engine keeps its ordinary sense. |
| `fleet` | A per-file short-form key making the named Fleet and supplying its owner to every Agent instance defined in that file (SCT-011). An Agent in another file states its own owner unless that file supplies one. |
| `manages` | A short-form key for an Interface's scope Conduits, or an Agent's Conduits to its own Fleet, with a role of `manage` or `view` (SCT-012). Nothing besides these ordinary Conduits is stored. |
| kind | The value of a framed document's `kind`. There are eleven: the six families and the five kinds of contract `Type`, `Capability`, `Operation`, `Requirement` and `Schema` (OBJ-020). A manifest has no `kind` (MAN-003). |
| object | A template or an instance of one of the six families. A contract is not an object (SUB-008). A JSON object is called a map: `object` is otherwise only the JSON Schema type, and the name of the core schema `object.v1`, with which a result names an object. |
| document | One template, instance or contract written out in YAML or equivalent JSON (SCH-013). Its framed form carries `apiVersion`, `kind` and `metadata`; only a framed instance may leave `metadata` out (OBJ-013). A sectioned document writes named definitions and templates without a frame and translates into framed documents (SCT-001 to SCT-016). A YAML file can hold several documents, and a JSON file one document or an array (SCH-018). Within one project or package names are unique across documents and implementations (NAM-027). The schemas of framed and sectioned documents are under [schemas/](schemas/README.md). A manifest is not a document in this sense. |
| project | The documents and the one manifest that are handed over together in one registration (SUB-005), or, as the one template that replaces another, its project's contract documents and its manifest, in a request to replace a template, which resolves it as a registration does (SUB-009). A directory is one way to hand them over, and every engine takes one (SUB-010): its documents are then the files in the directory itself whose names end in `.yaml`, `.yml` or `.json`, apart from the manifest, and nothing below it is read (MAN-001, MAN-011). Handing a directory over installs no package, and a registration whose manifest lists one that is not installed is rejected (SUB-010, PKG-006). A project that is handed over for registration is called a submitted project, whatever its manifest states, and its contracts are available to its own documents (SUB-008). A submitted project that holds a contract or lists an implementation states its `address`, by which they are named outside it (MAN-015, SUB-008). Two submissions may state one address, and the engine tells them apart by their digests (SUB-008). A package is a project that has been published. |
| published | Made available as an archive under an address. A package is a project that has been published: its manifest states its own `address` and `version` (PKG-017, MAN-004), and its archive is the one PKG-022 and MAN-013 describe. A submitted project is never published, whatever its manifest states: its `address` names its own contracts and implementations outside its documents (SUB-008), and may be neither the core package's nor that of an installed package (NAM-021, MAN-016). |
| submission | The documents handed to the engine together to be registered: templates, instances, contracts and the project's one manifest (SUB-005). Where a directory is submitted, they are the files MAN-011 names. They are a set, so their order has no meaning (SUB-001), and if any of them is rejected nothing in the submission is registered (SUB-003). |
| name | The readable lookup for an object, written in `metadata.name` or as an authored sectioned name (SCT-013): lowercase letters, digits and hyphens, starting with a letter, at most 63 characters (OBJ-001). No two objects of one kind that exist have the same name, templates and instances counted together (OBJ-002), and no two documents of one project or package have the same name, whatever their kinds (NAM-027). An instance that is given no name gets a generated one (OBJ-003). A name is fixed once its object is made: no document and no operation changes it (OBJ-011). Other names have their own rules: an export's name (NAM-004), a contract's name (CTR-001), the name of a member of a map (OBJ-022), and the names of an operation's inputs and outputs, which are the properties of its `inputSchema` and `outputSchema` (CTR-002). A label is not a name (OBJ-022). LIF-041 gives conflict where a tombstone holds a name even though the object no longer exists. |
| type | What specializes a family other than Conduit. It is a Type contract, which a template selects under `type` (TPL-002) and which states, among other things, the schema of an instance's `config`, the capabilities its instances offer and their controls (CTR-004). It may also state `records`, with `inputs` and `outputs`, which says what content the records about its instances keep, each false when left out, and `nodeSelector`, a label selector, which the labels fixed for an instance's node under ENR-010 must match (CTR-004, PLC-007). A type that states no `schema` puts no rule on `config`, and a Type of the family Pool offers the capability `pool-management.v1` (CTR-004). A type that offers a provider capability is a provider's type (PRV-001). A Conduit has no type. The only Type of family Fleet is the core `fleet.v1` (FLEET-001). |
| schema | The shape of valid data, written in JSON Schema 2020-12 as [schema-profile.md](schema-profile.md) narrows it: its applicator vocabulary and its validation vocabulary less `multipleOf`, with the keywords and formats the profile lists (SCH-001, SCH-002). |
| template | A framed document of one of the six families that has no `from`: `apiVersion`, `kind`, `metadata` and a `spec` that holds everything it declares (INS-001, OBJ-012). SCT-005 also writes one in `templates`, and SCT-006 makes one together with an inline instance. Instances are made from it. It can narrow what its type allows and cannot widen it (INS-014), and it has no lifecycle state (LIF-012). A template of a family that has a type and that writes no `config` means the same as one that writes `config: {}` (INS-024). |
| instance | One identified object made from a template. Its framed document has `from`, which names the template in one of the forms INS-025 gives, and the standard arguments of its family: `owner`, `consumer` and `target` are required, and `placement` and `runtime` may be left out. It may have `metadata` and `arguments`, and has no `spec` (INS-001, OBJ-013). SCT-006 also writes an instance as a sectioned definition, making its template alongside it where inline. Every instance comes from a template and has exactly one lifecycle state. For an Agent, `owner` names its Fleet. A Conduit may give `as`; a Fleet gives neither `arguments` nor standard arguments (OBJ-013, FLEET-001). |
| instantiate | Make an instance from a template and its arguments. It is what registering an instance document does. The instance's nested instances are made with it, and nothing is set up or opened (INS-016). |
| nested instantiation | An instantiation written inside a template, with no `kind`, `metadata` or `spec` (OBJ-014). It has two shapes. A declared Conduit holds `from`, and may hold `arguments`, `target` and `optional: true`. A Pool's entry holds `from`, and may hold `arguments` and `optional: true`. |
| nested instance | An instance made by a nested instantiation when the template that holds it is instantiated: the Conduit of a declared Conduit, or the Resource of a Pool's entry (INS-016, CON-002). It belongs to the instance whose resolved definition holds the nested instantiation. When a nested instance is retired, or has been removed, another is made in its place only by an explicit request, `register-replacement.v1`, which names the instance that holds the nested instantiation in `instance` and the declared Conduit or the entry in `nested`, from the template that the nested instantiation's `from` names as that template then stands (LIF-008, LIF-009). |
| input | A named value that a template, an Operation contract or a Requirement contract declares, and that whoever uses it supplies. A template's input is a member of the `inputs` map of its `spec` and holds `schema`, `to`, which lists one or more destinations, and optionally `default` and `optional: true` (INS-021). An Operation's inputs are the properties of its contract's `inputSchema`, a handle among them, and a property's schema may state a `default` (CTR-002). A Requirement's input holds `schema`, and may hold `default` and `optional: true` (CTR-005). An input's `default` is a literal value (OBJ-019), and it satisfies the input's own `schema` (SCH-019). An input that states a `default` may be left out, whether or not it is optional (OBJ-015). The engine fills in the `default` of an Operation's input that a request leaves out, before it dispatches; a control applies none (OPS-026, REV-006). A property that has a `default` in the schema of an input, and that is absent from a map which an argument supplies, takes that default before the argument is validated or compared, and the filled value is what is stored or sent: that is one rule for every schema that governs a supplied value (SCH-009). |
| argument | The value supplied for an input, written under `arguments`. An instance document, a nested instantiation and an applied requirement write the values themselves there (OBJ-013, NAM-019). An `arguments` map that is left out supplies no arguments, and is present and empty (OBJ-013, OBJ-014, NAM-019, INS-011). An argument of a server.json Package, a command-line argument that an item's `packageArguments` binds, and the `arguments` of a call of the Model Context Protocol are those standards' own (MAN-010, IFC-001). |
| standard argument | An argument that belongs to a family and not to a template, written as a top-level key of a framed instance document: `owner` for a Resource or an Agent, `placement` and `runtime` for an Agent or a Resource, and `consumer`, `target` and optional `as` for a Conduit (OBJ-013). A Fleet has none (FLEET-001). Standard arguments are accepted whatever inputs the template declares, and are rejected under `arguments` or on another family. |
| destination | A place in a template's `spec` where an input's value is assigned. It is a JSON Pointer in its string form whose root is the `spec`, and it does not use the `-` token (OBJ-016). INS-012 gives the closed list of the places it may reach, an entry's `placement` and `runtime` among them. |
| optional | A template's input, a Requirement's input, a declared Conduit and a Pool's entry are required unless they are marked `optional: true`, and an input that states a `default` may be left out without the mark (OBJ-015). An Operation's input or output is not marked: it is optional where its contract's `inputSchema` or `outputSchema` does not list it under `required`, and an optional output is one that a result may leave out (OBJ-015). The opening of an optional declared Conduit, and the setup of an optional entry's Resource, are optional parts of a setup: one that does not succeed does not keep the setup from succeeding (CON-004, POOL-013, OPS-022). The key `required` appears only as the schema keyword. |
| item | A member of a map or a list that is not a Pool's entry. An item of `packages` is a member of a manifest's `packages` map (MAN-005), an implementation item is a member of its `implementations` map (MAN-009), and the implementation-defined list is made of items. The promises do not say "manifest item". |

## Resolving and registration

| Term | Meaning |
| --- | --- |
| engine | A running program that implements this specification. It is the one word for the running thing; "implementation" is never used for it. It may be made of several parts, on several machines, where its conformance document says so under DL17: a promise that says what the engine keeps, records or does binds the whole, whichever part does it. In this version it is the only decision point, since it makes every access decision itself (ACC-002), and the only enforcement point (PRV-025). |
| resolving | The function from a set of documents, read against what already exists, the lifecycle state and the status of the objects that exist among it, to either the objects those documents make or diagnostics. It runs nothing and stores nothing. What it yields is called resolved: a resolved template, a resolved instance. The word is for documents and references. Placing an instance that is given no placement is not resolving: the engine asks the machine provider while it decides the registration (PLC-002, PRV-015). |
| resolve (a reference) | A reference resolves to the one thing it names. In an instance every reference is resolved when the instance is made, and the instance stores its resolved form (OBJ-009). A reference, or an item of `packages`, that reaches nothing is unresolved. A document whose selection, qualified `from` or `#name` names nothing is rejected (NAM-028), and a registration whose manifest lists a package that is not installed is rejected, so no check waits for a package (PKG-006). A template whose local reference names an object that does not exist is registered, with a diagnostic (OBJ-008). |
| resolved form (of a reference) | `{kind: <Kind>, id: <ID>}`: what an instance stores in the place of a reference, the kind and the ID of the object it resolved to (OBJ-009). Only the engine writes it, and every reference schema accepts it. It is the form an implementation receives, in its instance's configuration and in a filter's `arguments`, and the form inspecting shows (OBJ-021). An onward request may hold it in a request, because the engine handed it over; a request that an actor makes on its own behalf and that holds it reports invalid (LIF-031). |
| diagnostic | What resolving, or the installation of a package, returns about something that is wrong: it names the document or the package and the rule it breaks. There are two classes. One rejects. The other is reported and does not prevent registration (OBJ-008, NAM-008). A diagnostic is also how a request that is not dispatched says anything beyond its reason, in `diagnostics` in its result (IFC-025, LIF-020). Its form is the core schema `diagnostic.v1`, the `result` of SARIF 2.1.0 reduced to `ruleId`, `level`, `message.text` and logical locations that hold a JSON Pointer; `ruleId` is the ID of a promise. A result that reports invalid or conflict carries a diagnostic whose `level` is `error`, naming the promise that decided it, and one that reports refused carries none (IFC-025). Every reason carries one naming the deciding rule; refusals hold properties.refusal (IFC-050, ACC-056). |
| rejected | Said of a document for which resolving returns a diagnostic of the first class. Its registration is not dispatched and reports invalid (OBJ-023), or conflict where the document clashes with the name of an object that exists (OBJ-002, OBJ-025). A package is rejected when it is installed, and is then not available; the request to install it reports invalid (PKG-023). |
| register, registration | The operation `register.v1` of the core package, which takes a submission. It runs resolving on the submission and, if no document is rejected, stores the templates and instances the documents make, which then exist (SUB-006). Registering an instance document instantiates its template. Registration also makes and opens root's default Conduits under FLEET-005, and its result lists them. It has no other effect. `replace.v1` also takes a document, with the contracts and the manifest of its project, which it resolves as a registration does, and is a replace, not a registration: it registers nothing (SUB-009). A request for `register-replacement.v1` is a registration that takes no document: it is authorized, and reports, as registering the instance it makes would (LIF-009). Admitting a machine also makes a node, within root's request for `admit-machine.v1` (ENR-007, PLC-026); the engine makes the first-start objects, the node `local` among them, at first start (FST-001). A machine provider's report makes no node. An object that has been registered and has not been unregistered or removed is said to exist; "registered" as a description of an instance names a lifecycle state. |
| replace, replacement | To replace a template is to put another document of the same kind and name in its place, with `replace.v1`, which names the template's current revision (SUB-009). The document is handed over with its project, the project's contract documents as the input `contracts` and its manifest as the input `manifest`, and is resolved against them as a registration resolves a template: `#name` in it reaches that project and never the one that the template held before, whose contracts are identified by the digest of SUB-008, and the rules on a submitted project's manifest and address apply (SUB-009, NAM-022, PKG-029). A replace whose document is equal to the template as stored, and through which the template would keep exactly the packages, the project and the implementation items that it keeps, changes nothing and does not advance the revision (SUB-009). The request returns the template's revision after it in the output `revision`. It replaces one template and registers nothing, so it is not an apply of several templates (SUB-009). Submitting a document never replaces one (SUB-007), and instances made before keep what they resolved (INS-020). A replacement is something else: the new instance that `register-replacement.v1` makes for a nested instantiation whose instance is retired or has been removed (LIF-009). |
| install | Make a package available, so that what it exports can be reached by qualified references. It registers nothing (NAM-013). It is the operation `install.v1` of `management` (ACC-033), and a package is installed in no other way: a registration installs none of the packages its manifest lists, and neither does an engine that is handed a directory (PKG-006, SUB-010). PKG-023 to PKG-025 say what a request that installs nothing reports, PKG-026 rejects an archive whose digest is not the one asked for, PKG-027 says what a request for a package that is already installed reports, which is decided like any other request and from what is installed, with nothing fetched, PKG-028 rejects a package whose manifest lists one that is not installed, and PKG-029 has a request to install a package at the address that a submitted project states report conflict, while a template or an instance holds that submission. Who fetches the archive is PRV-017. |
| exists | An object exists from the moment it is made, by a registration, at first start or on a machine's admission, until it is unregistered or removed, whatever its lifecycle state (LIF-007, LIF-012, LIF-035, ENR-007, PLC-026). |
| ID | The stable identity of an object, which the engine gives it. An instance stores, for each of its references, the resolved form, which holds the ID of the object the reference resolved to (OBJ-009). A name is fixed, so a name comes to belong to another object only once the first no longer exists, and an instance's reference never follows it (OBJ-010, OBJ-011). A request that an actor makes on its own behalf names an object by a reference and never by its ID (LIF-031). A request for `set-up.v1`, `retire.v1`, `inspect.v1` or `unregister.v1` may carry the ID the actor expects in `expectedId`, which names nothing and grants nothing: where its reference resolves to an object with another ID, as after the name was given to another object once the first was removed (LIF-035), the request reports conflict and changes nothing (LIF-037). The engine also gives an ID to every invocation. The ID by which a credential of DL13 names the engine is not one: it is the engine's credential ID. `open.v1` and `close.v1` also accept `expectedId` (LIF-037). `lift.v1` names a tombstone by its ID (ACC-053). |
| the engine's credential ID | The ID by which a credential of DL13 names the engine, which the mechanism gives, and which only a credential that it issues to the engine names; `identity` gives it to a run in `engine-id`, so that a gate admits the engine and no instance (DL13, PRV-022, PRV-025). It is neither an ID that the engine gives nor the engine's ID for an invocation. |
| reference | A written pointer to an object: a map `{kind: <Kind>, name: <name>}`, or the name alone where the schema of the field fixes the kind (OBJ-006). `consumer` and `target` accept more than one kind and so are written with the kind (OBJ-013). The short form keeps this rule: `to` names its kind too, while a `fleet` value fixes Fleet (SCT-007, SCT-011). A request that an actor makes on its own behalf names an object by a reference (LIF-031). What an instance stores in its place is the resolved form. `from` names a template and has forms of its own (INS-025). |
| local reference | A reference that contains neither `#` nor `/`. It resolves only among the objects that exist, and is never looked up in a package (NAM-003). |
| qualified reference | A package's address, then `#`, then an export's name, such as `github.com/acme/conduit-history#shared-reviewer` (NAM-002). From outside a package it is the only way to reach what the package exports, and it never carries a version (NAM-005). A submitted project's contract or implementation is reached in the same form outside the project's own documents, `address#name`, with the address its manifest states, which names it in every submission at that address (SUB-008). A document does not use one for something in its own project or package (NAM-022). |
| `#name` | `#` followed by a name, with no address: a reference to the document, or the implementation, of that name in the same project or package as the document that holds it. A document uses this form, and never a qualified reference, for something in its own project or package (NAM-022). It carries no kind, so no two documents of one project or package share a name, and no implementation has the name of a document (NAM-027). A selection may be written this way (NAM-018), and so may a `$ref` to a Schema contract (SCH-015) and the `from` of an instance (INS-025). Written as `from` in a submitted project, whose templates are registered, it resolves as the bare name does, among the templates that exist (NAM-022). Anywhere else, a `#name` that names no document and no implementation of its own project or package makes the document that holds it rejected (NAM-028). Outside its project, on the wire and in a bound, a submitted project's contract is written `address#name` (SUB-008). Only the core package's own documents write their own address in full. |
| reference to a Pool's entry | `{kind: Pool, name: <pool>, entry: <entry>}`, written outside the Pool's template. It resolves to the Resource of that entry that is not retired (POOL-014). |
| entry reference | `{entry: name}`: one entry's reference to another entry of the same Pool template, rejected anywhere else (POOL-005). It resolves to the other entry's Resource when the Pool is instantiated (POOL-006). |
| reference schema | One of the Schema contracts that the core package exports for references: `reference.v1`, `interface-reference.v1`, `agent-reference.v1`, `resource-reference.v1`, `pool-reference.v1`, `conduit-reference.v1`, `actor-reference.v1`, `consumer-reference.v1`, `target-reference.v1`, `entry-reference.v1`, `pool-entry-reference.v1` and `secret-reference.v1`. A value inside `config` or `arguments` is a reference only where a reference schema governs its place, directly, as the `items` of a list, or as a branch of `anyOf` or `oneOf`, a `$ref` standing for the schema it leads to; any other value is data and is never rewritten (OBJ-021). `secret-reference.v1` governs a place under a narrower rule: directly, as `items`, or as a branch beside `{type: null}` alone (SEC-001). Every reference schema also accepts the resolved form. Where an input's reference schema fixes the kind, a bare name is accepted for it (INS-006), except for `secret-reference.v1` (SEC-001). The Fleet owner uses `fleet-reference.v1` (FLEET-002). |

## Placement

| Term | Meaning |
| --- | --- |
| node | A Resource of core node.v1 that represents a machine the person controls: local at first start, every other node only on admission (ENR-007, PLC-026). It is owned by system, its own placement and has empty configuration, no capability and no control (PLC-008). Status holds fixed labels (ENR-010), and for an admitted node machine {provider, id, hostname} and enrollment. Another party's machine is never a node. No actor registers one (PLC-028, FST-006). |
| represent | What a node does for one machine until retired. An admitted node binds the triple of provider Resource, machine id and canonical hostname (PLC-026). A report with a different provider, id or hostname leaves it omitted and adds a condition (PLC-023); replacing the provider never rebinds it (PRV-013). local represents only the engine's hostname, trimmed and lowercased, the operating system's unless configured otherwise (DL5). An engine that restarts elsewhere or runs in parts keeps that hostname (DL17). A retired node represents none; re-admission makes another node, which may take the hostname again because engine-made objects get no tombstone (LIF-040). |
| placement | The node of an Agent or a Resource, held in the resolved form of a reference, with that node's ID. Each has exactly one, and no operation changes it (PLC-001, PLC-009). Interfaces, Pools, Fleets and Conduits have none (PLC-006), and a template gives none (PLC-005). Where a document gives none, an instance for which no item that is run is selected is placed on `local`, and the machine provider places any other, with `place.v1`, on a machine that it reports reachable and whose labels match the instance's label selector, and its placement is the node that represents that machine; where no machine provider exists, it is `local` (PLC-002, PRV-015). Where the provider is not ready or cannot place the instance now, the request that would instantiate it reports unavailable (PRV-015). A runtime provider, the machine provider and a package-source provider are always placed on `local` (PRV-002). |
| unreachable, gone | The two ways in which the machine provider reports a machine lost (PRV-014). Where a machine is reported unreachable, a request or a hook that would be dispatched to an instance placed on its node reports unavailable, apart from a read of a secret that the machine provider's run needs, and nothing is retired (PLC-023, PRV-026). A machine that the latest report omits counts as reported unreachable until a report gives it a state (PLC-023). Where it is reported gone, the engine declares its node lost, which retires the node and every instance placed on it (PLC-024). |
| shared-host requirement | The requirement `shared-host.v1` of the core package, applied to a Conduit: the `kubernetes.io/hostname` labels fixed for its consumer's node and for its target's node are equal. The engine decides it once, when the Conduit is instantiated, and a Conduit for which it does not hold, or one of whose ends has no placement or is one for which no item that is run is selected, and so runs on no machine, is not instantiated (PLC-013, CON-006). The engine applies it itself and never sends it, so it is not a filter (CON-018). |
| value tied to a node | A value that has its meaning only at one node, such as an absolute path. It is interpreted only by the instance's implementation at the instance's placement, and the engine never interprets it anywhere else (PLC-020). |

| first start | The first time an engine is started. After it the first-start objects exist, each ready, with the three open Conduits of `root`, and nothing else (FST-001 to FST-003). |
| first-start object | One of the Pool `system`, the node `local`, the Resources `management` and `access`, and the Interface `root`. Each is an instance of a template that the core package exports, under the names `system`, `node`, `management`, `access` and `root` (FST-005), and none is retired or unregistered: no actor's request does it (LIF-022), and a report of the machine provider about the machine that `local` represents retires nothing (PLC-023, PLC-024). Each is identified by its ID, and its name, like every name, is fixed (FST-001, OBJ-011). No instance document is made from those five templates: the engine alone makes nodes (FST-006, PLC-026). The three Conduits of `root` that exist from first start are not first-start objects; none is closed at an actor's request (ACC-024). |
| `system` | The Pool that exists from first start, also written "the system Pool", of the basic Pool type `pool.v1`. It owns the nodes, the Resources `management` and `access`, and the machine provider and every package-source provider (PRV-013). |
| `management` | The Resource that authorizes registering, replacing and unregistering objects; setting up, retiring and inspecting Interfaces, Pools and Fleets; inspecting Conduits and templates; installing packages; and operations reserved to root (ACC-033). Its capability is `object-management.v1`. Registering a Resource or Agent into a live existing owner also needs that owner. A Resource's owning Pool or an Agent's owning Fleet authorizes its setup, retirement, inspection and reconciliation. Inspection and reconciliation go through `management` where that owner is retired or the object no longer exists; the latter reports invalid when inspecting and records only the outcome when reconciling. Access to `management` carries no bound and supports no filter (CON-028, CON-022). It cannot be narrowed to a template; a broker supplies narrower access (ACC-030). ACC-057 reserves registering Agents to root on its own behalf. |
| `access` | The Resource whose operations open and close Conduits and lift tombstones (ACC-006, ACC-012, ACC-053). Its capability is `access-control.v1`. |
| root Interface | The Interface `root`, the only actor with access at first start. It has three declared open Conduits, to `management`, `access` and `system` (FST-002), and a default Conduit to each later Pool and Fleet (FLEET-005). Its Conduit to `access` is unbounded and lists `lift.v1` (ACC-022). Root alone opens or registers a Conduit whose consumer is root (ACC-054), and closes its own Conduits except the first-start and default ones (ACC-024). Declaring a node lost, purging records and the three enrollment verbs are reserved to it (ACC-032); enrollment actions and machine evidence appear only at its own panel (PND-008). It alone opens a Conduit listing `get-secret.v1` (SEC-008) and registers Agents (ACC-057). |
| reserved to the root Interface | Said of an operation dispatched only when the root Interface asks (ACC-032). Its Operation contract carries reservedToRoot: true (CTR-002). Only core Operation contracts may carry it (CTR-009), and only a core capability may list one (CTR-003). The five contracts are declare-lost.v1, purge.v1, enroll-machine.v1, admit-machine.v1 and refuse-machine.v1. |

## Relationships

| Term | Meaning |
| --- | --- |
| Conduit | One of the six families. A Conduit is a relationship between exactly one consumer and exactly one target for exactly one capability (CON-001). While it is open it permits exactly the operations it lists, on its target (ACC-003), and once its consumer is retired only the requests of the consumer's retirement (ACC-039). It has no type and no placement. |
| standard Conduit template | A package-exported Conduit template for a common use of a capability, such as `read`, `read-write` or `turn`. Authors refer to it with `from`; PKG-031 recommends keeping its operation list across releases and using a new template for wider access. |
| default Conduit | The Conduit the engine makes and opens from root to each Pool or Fleet within its registration, from `root-pool` or `root-fleet`, with a generated name and local name equal to the target's (FLEET-005). No request closes it; retirement of its target does (ACC-024, CON-008). The declared `system` Conduit serves this role from first start (FST-002). |
| provenance | The state a Conduit keeps from its first opening: the caller, sending instance, invocation and authorizing Conduit or Conduits; for an engine-made Conduit, the cause `first-start` or `default` (ACC-044). Inspection and inventory show it, and the tombstone keeps it. A purge never removes it. |
| tombstone | State kept apart from records for what was closed or retired, until lifted. It retains the object's ID and names, its owner and provenance, the cause, who closed or retired it, and optional `within`, absent meaning the engine (LIF-040). It gives conflict on matching registration or opening (LIF-041). Objects the engine makes get none. |
| lift | Remove a named tombstone, by `lift.v1` of `access`, within the caller's bound. A caused tombstone is removed only where that same authority covers lifting it independently (ACC-053). A lift registers nothing and opens nothing. |
| inventory | The part of inspecting an instance other than a Conduit that shows its consumed and targeting Conduits in full, their tombstones, and an Agent's own tools reach apart, including the target's own tools on an open consumed Conduit that can start its model work, one hop only, to whoever may inspect that instance, with no counts (LIF-013). |
| scope | A holder's open Conduits listing `inspect.v1` to Pools and Fleets other than `system`, whatever templates made them. A holder is an Interface, or an Agent for its own Fleet. Inspection computes it from these Conduits; no Scope object or separate stored set exists (LIF-013). |
| consumer | The instance that makes requests through a Conduit. It is an Interface, an Agent or a Resource (OBJ-013). |
| target | The instance that receives them, and so the instance a request is made of. It is an Interface, an Agent, a Resource or a Pool (OBJ-013). In the promises the word is used only for this end of a Conduit. |
| capability | A Capability contract: a list of operations (CTR-003). A type's contract lists the capabilities its instances offer, and a Conduit names exactly one, which its target's type must offer (CON-021). Offering is not permission. |
| declared Conduit | A nested instantiation of a Conduit template, written in the `conduits` map of an Interface, Agent or Resource template (TPL-001). One Conduit is instantiated for it with each instance of that template, with the instance as its consumer (CON-002). Its opening is a part of that instance's setup, under the declared Conduit's name, and comes before the run and the setup hook (CON-004, TPL-012). A template that needs two capabilities of one target declares two Conduits. |
| open | Set up a Conduit. An open Conduit is one whose state is ready. It is opened by an operation of `access`, `open.v1` (ACC-006). A Conduit that is not open and either of whose ends is retired is not opened (CON-031); a request to open a Conduit that is already open succeeds and changes nothing (ACC-006). |
| close | Retire a Conduit. A closed Conduit is one whose state is retired: all the access it carried has ended, and it is never opened again (ACC-011, LIF-006). The operation is `close.v1` of `access` (ACC-012), and CON-008 says what else closes one: the retirement of its target, at once; that of its consumer, once the consumer's shutdown is confirmed, or at once where the consumer is declared lost or placed on a machine reported gone. From the moment its consumer is retired until it is closed, the Conduit permits only the requests of the consumer's retirement (ACC-039). Its shutdown is confirmed when it is closed, however it was closed (LIF-024), and it is then removed (LIF-035): its tools are no longer presented (IFC-013), a request through it reports refused (ACC-011), and one that names it reports invalid (OPS-029). |

## Access

| Term | Meaning |
| --- | --- |
| actor | An Interface or an Agent (IFC-021). Only an actor makes a request on its own behalf. |
| caller | The actor on whose behalf a request is made. For a request an actor makes on its own behalf it is that actor. For an onward request it is the caller of the invocation being served (IFC-020, IFC-021). A hook is dispatched for the caller of the setup, retirement or sign-in.v1 invocation it belongs to (TPL-017, TPL-018, PND-011), and the engine's read of a secret has the caller of the setup or the retirement it belongs to, or, where it reads again for a connection whose values it lost, that of the setup that made the connection, and, where it reads for a provider's run made again after the engine restarts, or the part of it that held that run stops, that of the setup that last asked for that run (SEC-011, SEC-023, PRV-026). Every call that the engine sends for a request or a hook has a caller (IFC-006). A request from which the engine could establish no instance has none, and is not dispatched (IFC-032, REC-002). A provider call carries the caller of the request it is made for, where it is made for one (PRV-005). |
| onward request | A request that an instance makes of another target in order to serve an invocation it received, a hook's among them. It names that invocation, is permitted only under the instance's own open Conduit to that target, and carries the caller and the filters of the invocation it serves: the filters on the Conduit that invocation was dispatched through, and those that invocation itself carried (ACC-016, ACC-017, ACC-018). It is dispatched only where each Conduit of its chain is open and the consumer of none of them is retired, the requests of that consumer's own retirement apart (ACC-034, ACC-039). |
| chain | Of an invocation: the invocations that it serves, directly or through others. An onward request serves the invocation it names (IFC-020), and a hook serves the invocation of `set-up.v1`, `retire.v1` or `sign-in.v1` it belongs to (ACC-017, PND-011). The Conduits of the chain are the Conduits through which the invocations of the chain were dispatched (ACC-034, ACC-039). The promises use the word for nothing else. |
| the instance that sent a request | For a request that an actor makes on its own behalf, that actor. For an onward request, the instance that makes it, which is not the caller. The promises also call it the sending instance. An idempotency key is scoped to it, as well as to the caller and the target (OPS-008), apart from a setup hook's or retire hook's, which is scoped to its instance alone (OPS-028). The parts of a setup that open a declared Conduit or set up an entry's Resource are requests of the instance that sent the setup, authorized by its Conduits (ACC-005, POOL-015). Reconciliation through a Pool or Fleet is limited by this sender under ACC-055. A hook counts as sent by the instance that sent the setup, retirement or sign-in.v1 invocation within which it ran. |
| serve | Do the work of. An instance serves an invocation that was dispatched to it and is in progress (IFC-028). An implementation serves each instance for which it is the selected implementation. |
| permitted | A request is permitted when an open Conduit from its consumer to its target lists the operation and every restriction that applies permits it (ACC-001, ACC-008). ACC-033 fixes the target for each management request, and says the request is authorized against that target. Through a Conduit whose consumer is retired, only the requests of the consumer's retirement are permitted (ACC-039). An instance's request for `get-secret.v1` is never permitted, whatever Conduit lists it (ACC-003, SEC-007). A request that is not permitted reports refused. Refusals explain the missing permission with the disclosure of ACC-056. |
| access decision | The engine's own decision whether a request is permitted. It is made before the target's implementation is invoked, and it is recorded (ACC-002, REC-001). It is made anew for each request, from the Conduits as they stand, and no earlier decision is reused (ACC-036); an engine that runs as several parts reads that state as it stands for every decision (DL17). Where their state cannot be established the request reports unavailable, and nothing else about it is examined or reported (ACC-037, OPS-023). No access decision is made for a provider call (PRV-005). Unestablished access state carries one ACC-037 diagnostic naming no object. |
| decision point | What makes access decisions, as NIST's policy decision point computes them for a policy enforcement point. In this version the engine is the only one, and the word names the role that an enforcement point relies on; no promise uses it. |
| enforcement point | What a request passes through on its way to a server, and which passes it on only once a decision point has permitted it, as NIST's policy enforcement point enforces what its decision point decides. In this version the engine is the only one (PRV-025). A request that the engine sends to a server that it does not run itself carries the proof of an enforcement point, by the mechanism of DL13, which that server's gate checks (PRV-025, IFC-017, IFC-041); the proof is the engine's own, never what a consumer presented (IFC-030). A restriction is mediated in that it applies to the requests that pass through one (ACC-027). |
| right to open | What an actor has when it is the consumer of an open Conduit to `access` that lists the operation that opens Conduits (ACC-006). It is limited by that Conduit's bound, and is passed on only as it is or narrower (ACC-030). |
| bound | The limit that a Conduit to `access` carries on which Conduits its consumer may open and close. It is a restriction that the engine applies itself and never sends, so it is not a filter (ACC-029, CON-018). It is written as the core package's requirement `bound.v1`, applied in the `requirements` of the Conduit's template with the arguments `pools`, `targets` and `operations`. Naming a Pool covers the Pool itself and every Resource it owns, whenever instantiated (ACC-029). It names operations by qualified reference: those of an installed package, or of a submitted project as `address#name`, compared as names and never resolved, so a project's own documents may name its operations there (ACC-029). One bound is within another when every Pool and every target it names is covered by the other, and every operation it names is one the other names (ACC-030). A Conduit to `access` that applies no `bound.v1` has no bound and is unlimited, as the root Interface's is (ACC-022): it is within another only if that other has none (ACC-030). A Conduit to any other target that applies one is not instantiated, and a template that applies it twice is rejected (CON-028). A bound limits by Pools, targets and operations and never by filters, so a right to open trusts its consumer with unfiltered access within its bound, whatever filters apply to the Conduits that its consumer already has (ACC-030, ACC-009). [What access does not narrow](README.md#what-access-does-not-narrow) states what that leaves open. An individual target and each Pool keep the ID they resolved to; a Fleet in `targets` covers that Fleet alone (ACC-029). A bound also limits closing, lifting and reconciliation through `access` (ACC-012, ACC-053, ACC-055). |
| broker | A Resource with an operation through which an actor gets narrower access to `management` than a Conduit to `management` carries, such as registering instances of one approved template and no other. The broker's own contract and configuration allow only that, and its implementation, which is trusted to keep them, makes the request as an onward request through the broker's own Conduit to `management`, which authorizes it (ACC-016, ACC-033). The actor is the consumer of a Conduit to the broker that lists that operation and applies no filter, since the onward request would carry the filter and `management` cannot apply it (ACC-017, ACC-015), and of none to `management`. The narrowing is the broker's and not the engine's: the broker's own Conduit to `management` is as wide as any (ACC-030). A broker is an ordinary Resource, of no family or kind of contract of its own. |
| requirement | A Requirement contract: something that must hold for a relationship or its use. Its `spec` holds `inputs` alone, and it is applied only to a Conduit, in the `requirements` map of the Conduit's template (CTR-005, CON-018). A requirement of the core package, `bound.v1` or `shared-host.v1`, is applied by the engine itself and never sent; any other is a filter (CTR-005). Several requirements are applied side by side; none is made of others. |
| applied requirement | A requirement as it is written where it is applied: `requirement`, the selection of the contract, and `arguments`, which may be left out, are the values themselves and are checked against the inputs the contract declares (NAM-019). |
| filter | A requirement other than one of the core package's, applied to a Conduit in its template's `requirements` (CTR-005, CON-018). The implementations that the target has selected for the operations the Conduit lists must state its requirement in `supports`, or the Conduit is not instantiated (CON-022); they are sent it with each request through the Conduit, and apply it (IFC-018, IFC-019). It applies to requests through that Conduit only (ACC-009), and to the onward requests and hooks that carry it from them (ACC-017, ACC-018). It judges a call: a repeat to which it applies and that is not dispatched is judged by no filter, and gives only an outcome already recorded or reports conflict, so no such repeat is given outputs that the filter has not judged (ACC-008, OPS-009, OPS-024, OPS-034). A filter limits no other Conduit of its consumer, and none that its consumer may open under a right to open (ACC-009, ACC-030). |
| restriction | A filter or a bound that applies to a request, including a filter that an onward request carries from the invocation it serves, and one that a hook carries from its setup or retirement (ACC-009, ACC-017, ACC-018). Only filters are sent to an implementation (IFC-018). A restriction only narrows: none permits what the Conduit does not (ACC-008). |
| narrow | Make what is permitted, or what is accepted, smaller and never larger. A template narrows what its type allows (INS-014) and a control's inputs (TPL-010), which the tool presented for the control shows (IFC-033), and a restriction only narrows (ACC-008). Access is narrowed by closing a Conduit and opening one that lists fewer operations or applies further filters (ACC-011, LIF-001). The key `narrows` is gone (CTR-005). |
| mediated | Said of a restriction that applies to requests that pass through an enforcement point, which in this version is the engine alone. It is one of the two values that inspecting a Conduit reports for each restriction on it, and in this version it is the value reported for every restriction (ACC-027). |
| enforced | Said of a restriction that the consumer is also kept from going around, because the runtime provider that runs the consumer confines it, as that provider's contract states, so that it reaches targets only through an enforcement point (ACC-027). Such a provider is picked through `runtime` (PRV-006). It is the other value that inspecting a Conduit reports; in this version no restriction is reported as enforced (ACC-027). A gate keeps other callers from a target's server, but does not confine the consumer, which may still reach by its own means what the target's implementation reaches, so it makes no restriction enforced (ACC-027, PRV-025). |
| own tools | Tools supplied by an Agent's client, such as shell, code execution, file edits and network access. A Type declares them with `toolsDirectory`: a string at its pointer in the resolved configuration gives the tools its contract states for that case, working in the directory it names (CTR-014). Their reach passes through no enforcement point and is reported as neither enforced nor mediated in this version, whatever the runtime provider. A null gives none of the own tools that a string turns on, leaving what the Type's contract states for that case. Inspection shows this reach apart, on the Agent and one hop out on holders of open Conduits that can start its model work (LIF-013). Confinement and its limits belong to the runtime provider (PRV-006). |
| `supports` | The key of an implementation item reached by `command`, `package` or `remote` that lists the requirements the implementation can apply as filters (PKG-019). An implementation supports a requirement when it states the requirement there, matched by its address and its export name (CON-022). A plain implementation supports none (PKG-020), and `engine` states none, because the engine applies the core package's requirements itself (MAN-012). A request or a hook that carries a filter whose requirement the implementation it would be dispatched to does not support reports unavailable (ACC-015). |

## Requests and operations

| Term | Meaning |
| --- | --- |
| operation | A callable action with named inputs and outputs, defined by an Operation contract, whose `inputSchema` and `outputSchema` are written as the Model Context Protocol writes a tool's (CTR-002, CTR-012). Each holds `type: object` at its root and may use there any keyword of the schema profile, such as a `oneOf` that says which inputs are present, apart from a control's, which holds there only `type`, `properties`, `required` and `additionalProperties` (CTR-012). |
| output | A named value that an operation produces: a property of its contract's `outputSchema` (CTR-002). A result that is not an error holds the outputs in its `structuredContent`, keyed by name (IFC-001, IFC-025). An output that `outputSchema` does not list under `required` may be left out of a result (OBJ-015), and a declared output that fails validation makes the outcome unknown (OPS-007). |
| management verb | An operation of `object-management.v1`, offered by `management`; `access-control.v1`, offered by `access`; `pool-management.v1`, offered by every Pool; or `fleet-management.v1`, offered by every Fleet (CON-024, OPS-019). These include registration, inspection, listing, setup, retirement, reconciliation, replacement, installation, declaring lost, purging, cascades, opening, closing and lifting. A control, hook, provider operation or `get-secret.v1` is not one. This test selects the reconciliation row of ACC-033. |
| setup hook, retire hook, sign-in hooks, hook | The core operations `setup-hook.v1`, `retire-hook.v1`, `sign-in-hook.v1`, `account-hook.v1` and `sign-out-hook.v1`, which a template selects in its `implementation` map like any operation, or takes the default of its type where the type requires the hook (TPL-004, TPL-017, TPL-018). A default that a type states for a hook it does not require is not used: a template of that type that selects no implementation for the hook has none (TPL-004), and installation or resolving reports that default, when it reads the type, in a diagnostic that does not reject (CTR-004). The setup hook is the instance's own setup work: the engine dispatches it as the last part of each setup, once the declared Conduits or entries, the run and the connections are up and any account check and undo have ended (TPL-012, TPL-017). The retire hook is the instance's own work before its run is stopped: the engine dispatches it within a retirement of an instance for which a setup was ever dispatched, asking first for the run where its runtime provider reports it `stopped`, or connecting to its `remote` item where no connection to it lasts whose values the engine holds (TPL-018). The three sign-in hooks are `sign-in-hook.v1`, which obtains the URL elicitation, `account-hook.v1`, which reports the account, and `sign-out-hook.v1`, which undoes a different account; CTR-013 requires them and PND-010 and PND-011 give their order within sign-in.v1 or setup. "Hook", alone, means any of the five. A hook is not a request: the engine dispatches it to the implementation its instance selected, through no Conduit, for the caller of the setup, retirement or sign-in.v1 invocation, carrying that invocation's filters, of which in this version there are none (ACC-018, PND-011). The setup and retire hooks have idempotency keys scoped to the instance alone under OPS-028; its rules for repeats apply to those two hooks only. A request that the implementation makes while serving it is an onward request (ACC-018). None of the hooks starts model work (IMP-001, IMP-002, PND-010). |
| effect | What an operation's contract says, under `effect`, that it changes outside itself. An operation whose contract states none changes nothing outside itself (CTR-002). |
| call | One `tools/call` request of the Model Context Protocol: what a consumer sends the engine, and what the engine sends an implementation for a request, a hook or a provider call (IFC-001, IFC-006, PRV-005). |
| request | The asking for one operation on one target. There are three kinds: a request that an actor makes on its own behalf; an onward request, that an instance makes to serve an invocation it received (IFC-021); and the engine's read of a secret, which it makes for an instance's run or connection through that instance's own Conduit, with the caller of the setup or retirement it belongs to (SEC-010, SEC-011, SEC-023, PRV-026). A hook and a provider call are not requests (ACC-018, PRV-005). Once an invocation has ended no request is dispatched on its behalf, and the engine makes none for work that an operation arranged, apart from the read that SEC-023 makes again for a connection that a setup made, and the read for a provider's run that PRV-026 asks for again after the engine restarts, or the part of it that held that run stops (ACC-019). Every request ends in exactly one of the seven ways listed [below](#how-a-request-ends). The Model Context Protocol calls any JSON-RPC request a request, a call among them; in the promises a request is only the asking, which a call carries (IFC-001). |
| dispatch | The engine's passing of a request, a hook or a provider call to the implementation that is to serve it, after the engine's own checks. What is not dispatched reaches no implementation. |
| invocation | What a dispatched request or hook begins: one carrying-out of an operation on a target for a caller. It has an ID that the engine gives it, a state, and one or more attempts. Where the engine runs as several parts, at most one of them acts on any one invocation, as the store of the engine's own state enforces (DL17). A provider call begins none: it carries the ID of the invocation within which it is made, where there is one (PRV-005). |
| the engine's ID for an invocation | The ID the engine gives every invocation, whether or not the caller supplied an idempotency key. It is sent to the implementation (IFC-006), is what an onward request names to say which invocation it serves (IFC-020), is returned to a consumer in the result's `_meta`, also on a repeat that reports conflict (IFC-025, OPS-032, OPS-034), is what `reconcile.v1` names (OPS-014), is held in records (REC-002), and, while the invocation's outcome is unknown, is listed in `unreconciled` in the status of the instance it was dispatched to or names (LIF-013). |
| `serving` | The engine's ID for the invocation that another invocation serves. An onward request names in the key `io.github.shrav-k.conduit/serving` the invocation it serves, which the engine reads and does not send on (IFC-020). A record holds it in the member `serving` of its `data`: for an onward request, the invocation it names; for a hook, a read of a secret, or a part that is an invocation of its own, the setup, retirement or sign-in.v1 invocation it belongs to; for a read made again under SEC-023, the setup that made the connection; and for a read for a provider's run that PRV-026 asks for again after the engine restarts, or the part of it that held that run stops, the setup that last asked for that run. A provider call's record has none (REC-002). Once an invocation has ended, a request that names it there reports refused (ACC-019, IFC-028). |
| idempotency key | A value a caller may attach to a request so that repeats of it are recognized, as the IETF's draft of the HTTP header `Idempotency-Key` defines one. It is a non-empty string, sent in the key `io.github.shrav-k.conduit/idempotencyKey` (IFC-023). It is scoped to that caller, that target and the instance that sent the request, and at most one invocation exists for one of each and one idempotency key (OPS-008). A request that carries none is always a new invocation (OPS-011). The engine gives each setup hook and retire hook one of its own, derived from the instance's ID and the hook's operation and scoped to the instance alone, so that a further setup or retirement dispatches the hook again only as a repeat would be (OPS-028). |
| repeat | A request from the same instance, with the same caller, target, idempotency key and contents, as an earlier one that began an invocation. The contents are the same when both name the same operation and their arguments are equal, judged after defaults are filled in (OPS-009). A repeat is not a new request. Where the invocation succeeded and no filter applies to the repeat, nothing is dispatched and the result is that outcome with the outputs, where the operation declares none or the engine still keeps them (OPS-009), and otherwise the repeat reports conflict (OPS-034). Where a filter applies to it, no outputs that the filter has not judged now are given: an operation whose contract states no `effect`, that is not a control and that does not start model work, as IFC-033 tests for `readOnlyHint`, is dispatched again as a new attempt (OPS-024); any other that declares no outputs is answered from its outcome alone (OPS-009); and any other that declares outputs reports conflict (OPS-034); such a repeat that is not dispatched is judged by no filter, and gives only an outcome already recorded or reports conflict (ACC-008). Where the invocation has not ended, the repeat reports conflict, with the engine's ID for it (OPS-032), the `ruleId` of its error diagnostic telling it from OPS-034's; where its outcome is unknown or failed, the repeat is dispatched as a new attempt, or, for unknown, answered with the state unknown (OPS-012, OPS-024). A request that matches an earlier one that ended with a reason, where that one neither began nor repeated an invocation that the engine keeps, is not a repeat: it is a new request, decided afresh (OPS-025). |
| attempt, new attempt | An attempt is one dispatch of an invocation. A new attempt is a further dispatch of the same invocation, with the same idempotency key. It is made only for a repeat: after the outcome failed; after the outcome succeeded, where a filter applies to the repeat and the operation's contract states no `effect`, it is not a control and it does not start model work, so that the filter decides afresh (OPS-024); or after the outcome unknown where the operation's contract declares `deduplicates: true` and the implementation is not plain (OPS-012). Where the implementation answers a new attempt after success with a reason in place of an outcome, the repeat reports that reason, and the invocation's outcome and the outputs kept for it are as they were (OPS-024). Nothing is dispatched again without a repeat (IMP-007). An invocation counts as dispatched through the Conduit of its latest attempt (OPS-024). A setup hook or retire hook that failed is dispatched as a new attempt, with the idempotency key the engine gave it, when a further setup or retirement comes to it; one whose outcome is unknown is not dispatched again until it is reconciled, since neither hook's contract declares `deduplicates: true`, and one that succeeded is not dispatched again (OPS-021, OPS-028). |
| `deduplicates` | A mark of an Operation contract. An operation whose contract declares `deduplicates: true` is one whose implementation recognizes an idempotency key that it has already been sent and applies the effect at most once for it (CTR-002). Only then is a repeat after the outcome unknown dispatched as a new attempt (OPS-012). A plain implementation is sent no idempotency key and never counts as deduplicating (PKG-020). It is not the Model Context Protocol's `idempotentHint`, which hints that calling the tool again with the same arguments has no further effect: the engine passes that hint into the tool's `annotations` (IFC-033) and never decides a new attempt by it (OPS-012). |
| in progress | Said of an invocation that has been dispatched and has not ended (IFC-028). A repeat of its request reports conflict, with the engine's ID for it (OPS-032). |
| the invocation's state | In progress, or the invocation's outcome. The engine keeps it as its own state, apart from the records, with the rest of what repeats and reconciliations need, and no purge touches it (OPS-008). How the digest of an invocation's contents is computed is DL2 of the implementation-defined list. In a status the key `state` holds the lifecycle state. |
| outcome | How an invocation ended: succeeded, failed or unknown (OPS-001). A pending action has an answer instead (PND-003). |
| reason | Why a request ended with no outcome: refused, invalid, conflict or unavailable (OPS-005). Every reason carries its deciding diagnostic (IFC-050). |
| result | What a request returns: a tool result of the Model Context Protocol, with the operation's outputs in its `structuredContent` and Conduit's keys in its `_meta` (IFC-001, IFC-025). A result that the engine gives a consumer has `isError` true where the request ended with a reason or its outcome is failed or unknown, and in no other case; such a result carries none of the operation's outputs, `diagnostics` apart. Any other result holds declared outputs in `structuredContent`; where the operation declares no outputs, that member is absent and its tool has no `outputSchema` (IFC-025, IFC-033). A result whose invocation succeeded holds its outputs even where the Conduit through which it was dispatched was closed while it ran (ACC-034). A call that names a tool the engine does not present is answered, at the baseline revision, with no result: the engine answers it with the protocol's error, which carries the reason, and at a revision at which a tool result answers it, that result carries the reason (IFC-012, IFC-025). A request that the protocol has a server reject is answered with the protocol's error and no result (IFC-036). The promises use this one word for it, and "answer" only as a verb. Every reason has a deciding diagnostic, and the first error text explains it (IFC-050). |
| reconcile | Record, with what was checked, that the effect of an invocation whose outcome is unknown did occur or did not. The outcome then becomes succeeded or failed (OPS-014). It is the operation `reconcile.v1`, which names the invocation by the engine's ID for it. For an invocation of a management verb it is authorized against the target that authorized the request being reconciled. For any other invocation, of a control or of any other operation, it is authorized against the target that manages the instance the invocation was dispatched to: the Pool that owns it where it is a Resource, and `management` otherwise, or where that Pool is retired (ACC-033). Where the instance no longer exists, it is authorized against `management`, records the outcome and stores nothing. A request that names an invocation whose outcome is not unknown reports conflict (OPS-030). No capability has to include `reconcile.v1` beside the three that hold management verbs. LIF-028 says what else the reconciliation of a setup, an open, a retirement or a close changes, and REV-010 that of a control. A setup or a retirement of unknown outcome that asked for a run or its stop is settled by reading the condition `Running` (PRV-009). An actor finds the invocations of unknown outcome that concern an instance, a hook's among them, in `unreconciled` in its status, which no purge shortens (LIF-013, OPS-014). A reconciliation states `revision` only for a control that it records as having taken effect on an instance that exists and is not retired; a request that states it anywhere else reports invalid (OPS-031, REV-010). The noun is reconciliation. It is not a Kubernetes controller's reconcile: nothing is driven toward what was declared (OBS-004). |
| cancel | Ask an invocation that is in progress to stop, by the protocol's own cancellation of the request that dispatched it: `notifications/cancelled` on stdio, the close of the response stream on Streamable HTTP, or `tasks/cancel` for a task. The engine passes the cancellation on to the implementation by the same means. The outcome of a cancelled invocation is unknown, unless its implementation confirms that nothing was done (OPS-027). A connection over Streamable HTTP that the engine sees drop cancels the invocation for the engine; whether and when the implementation learns of it is its transport's and, behind a gate, the gate's, so after a cut in which packets are dropped the work may run to its end (OPS-027, PRV-025). Where the engine implements the invocation in parts, as it does a setup or a retirement, it passes the cancellation on to each part in progress, no later part begins, and every retirement still asks for its stop (OPS-027, TPL-012, TPL-009). |
| model work | A turn of an Agent's model, started or continued. It starts only as the effect of an operation whose contract is marked `startsModelWork: true`, dispatched through an open Conduit that lists that operation (IMP-001, IMP-003). Neither setup, retirement nor a hook starts it (IMP-002), and an onward request that serves an invocation not so marked may not start it (IMP-008). |

### How a request ends

Every request ends in exactly one of these seven ways. No other word is used for them.

| It has | Word | Meaning |
| --- | --- | --- |
| An outcome | succeeded | The effect the operation's contract describes has occurred (OPS-002). |
| | failed | The effect has not occurred, in whole or in part (OPS-003). |
| | unknown | It cannot be confirmed that the effect occurred or that it did not, or it occurred only in part (OPS-004, OPS-007). |
| A reason, and no outcome | refused | The request is not permitted, whoever asks and whatever the cause: for example no open Conduit lists the operation, a restriction forbids it, a bound does not cover it, the operation is reserved to the root Interface, or it is an instance's request for `get-secret.v1`. |
| | invalid | The request cannot be read, or does not satisfy a schema or a rule for what it asks, such as a document that is rejected, a change that names no revision, a request through a Conduit that lists the operation and that names an object or an invocation that does not exist (OPS-029), or a request that an actor makes on its own behalf and that holds the resolved form of a reference (LIF-031). |
| | conflict | The request does not match the current revision or state of what it addresses, or clashes with something that exists, such as a name or an idempotency key already used with other contents, another setup, retirement or change of the same instance that has not ended (REV-014), or an invocation that it repeats and that has not ended (OPS-032), or that succeeded, of an operation that declares outputs, where the engine no longer keeps them, or where a filter applies to the repeat and the operation is not one that is dispatched again (OPS-034). |
| | unavailable | The request could not be checked or carried out now: for example a restriction cannot be evaluated or applied, the target is not ready, the machine of the target's node is reported unreachable, a secret its implementation needs could not be read, the machine provider cannot place an instance now, or the state of the Conduits cannot be established. |

A request that has an outcome was dispatched, or is a repeat that OPS-009 or OPS-012 answers
with the outcome of the invocation it repeats (OPS-005). A part of a setup for what is already
done, an open Conduit, a ready Resource or a running run, counts as succeeded with nothing
dispatched (CON-004, POOL-013, PRV-007). A request that has a reason was not dispatched, with
one exception: an implementation that carries Conduit's keys answers refused or unavailable in
place of an outcome, where a restriction it was sent forbids the request or cannot be applied,
and it has then performed nothing (IFC-026, IFC-027). Where more than one reason applies to a
request that is not dispatched, one is reported, in this order: invalid if the request cannot
be read; otherwise refused, or unavailable where the access decision cannot be made, in which
case nothing else about the request is examined or reported (ACC-037); then invalid; then
conflict; then unavailable for any other cause (OPS-023). A result that carries both an outcome
and a reason has the outcome unknown, and so has an implementation's result whose `isError`
disagrees with the outcome it states (IFC-009, OPS-007). A request that matches an earlier one
that ended with a reason, and that began no invocation and repeated none, is a new request and
is decided afresh (OPS-025). A repeat of an
invocation that has not ended, or of one that succeeded, of an operation that declares outputs,
where the engine no longer keeps them or where a filter applies to the repeat and OPS-024 does
not dispatch it again, is not dispatched and reports conflict, and its result holds the
engine's ID for the invocation (OPS-032, OPS-034). A hook, and every part of a setup or a
retirement, ends in one of the same seven ways (OPS-022, ACC-015, PLC-023).

## Implementations and the implementation interface

| Term | Meaning |
| --- | --- |
| implementation | What does the work behind an operation. A package's manifest, or a submitted project's, lists each one with the operations it implements and how it is reached, which is by exactly one of `command`, `package` and `remote` (PKG-019, MAN-009). An operation built from others is an ordinary implementation: a server that makes onward requests. In the core package's manifest alone, the implementation `engine` states none of the three, because the engine itself does that work (MAN-012), and the engine implements each operation that `engine` lists with no selection (TPL-004). Otherwise the word is never used for an engine. |
| implementation item | A member of a manifest's `implementations` map (MAN-009). It is reached by exactly one of `command`, a program and its arguments; `package`, one Package as the Model Context Protocol Registry's server.json gives it, in the version 2025-12-11, pinned by its `fileSha256` or, for an `oci` image, by a digest in its `identifier`; and `remote`, one Remote of server.json whose `type` is `streamable-http` (MAN-010). It may state `environment`, `packageArguments` or `headers`, which bind a variable, an argument of the Package's `packageArguments`, named by its `name` or, where it is positional, by its `valueHint`, or a header of the Remote to a place in the instance's configuration by a JSON Pointer, a place that the type's schema must require and must confine to a string, a number, a boolean or null, unless `secret-reference.v1` governs it (MAN-010, MAN-017, OBJ-016); `nodeSelector`, a label selector; `supports`; and `plain` with `tools` (PKG-019, PKG-020). An item reached by `remote` that is not plain stands at an `https` URL (IFC-044) and names no `Authorization` in its `headers` (IFC-043), and no item reached by `remote` implements an operation of `runtime-provider.v1`, `machine-provider.v1` or `package-source.v1` (PKG-030). A template is rejected whose item binds in its `environment` a variable that `identity` carries (MAN-018), or is reached by `remote` and binds a header to a secret, or serves `get-secret.v1`, at a URL to which SEC-024 lets no secret go, or stands at a loopback host on an engine that can restart on another machine or run as several parts (SEC-024). |
| item that is run | An implementation item reached by `command` or `package`. The instance's runtime provider runs it as the instance's run, and an Agent or a Resource has at most one, and an Interface or a Pool none: a template whose selected implementations include two, or one for an Interface or a Pool, is rejected (TPL-019, PRV-007). An item reached by `remote` is not run: the engine reaches it at its Remote's URL (IFC-041). |
| connection | The engine's connection to an implementation item to which it sends calls for an instance (IFC-017). Over stdio, to a process of the engine's own runner, it is the process's standard streams. Over Streamable HTTP it is Conduit's own notion and not the protocol's, because in the baseline revision of the Model Context Protocol that transport keeps no session and every HTTP request carries its own authorization: it is the engine's sending of HTTP requests to the URL at which it reaches the item, with what it holds to send on each (SEC-013). The connection to an item reached by `remote` is a part of a setup, and is what the promises mean where they speak of a connection that a setup or a retirement makes, or that lasts: it is made to serve one instance, within its setup, or within its retirement to serve its retire hook where no connection to the item lasts whose values the engine holds, over Streamable HTTP at the URL of the item's Remote, with the headers that its `headers` binds sent on every HTTP request of it, with the values of the configuration as it stood when the connection was made (TPL-012, TPL-018, IFC-017, IFC-041). To an item that is not plain it is made only at an `https` URL, once the server has proved who it is, and every HTTP request of it carries the proof of an enforcement point (IFC-017, IFC-041). It is the engine's holding of those headers' values: it lasts until a later setup's connection takes its place, the instance's retirement ends or the instance's node is declared lost, and a failed HTTP request does not end it (SEC-013, IFC-041). A secret that a header needs is read before it is made, held only for as long as it lasts, and sent only to a URL to which SEC-024 lets it go on the engine as it is configured then, so that one registered before the engine could restart on another machine is sent nowhere once it can (SEC-013, SEC-024); where the engine has lost the values, as after it restarts, it reads again, before its next HTTP request, each secret Resource that the setup which made the connection read, and a retirement connects anew to send its retire hook (SEC-023, TPL-018). Where a promise speaks of the connection on which a request travels, such as one that TLS secures, one that drops or goes silent, or the one on which a consumer's request reaches the engine, it means the transport's connection, as HTTP and TLS use the word, which holds no such values (IFC-012, IFC-017, IFC-022, OPS-027, PRV-018, PRV-025). |
| plain | Said of an implementation that is an existing server not written for this specification, marked `plain: true` in its implementation item (PKG-020). It receives none of Conduit's keys (IFC-007), supports no requirement and never counts as deduplicating, and its results are turned into outcomes by the table of IFC-010, in which an error of it is failed for an operation whose contract states no `effect`, that is not a control and whose contract is not marked `startsModelWork: true`, as IFC-033 tests for `readOnlyHint`, and for invalid parameters, and otherwise unknown. The protocol's error -32021 for a client capability that the call did not declare is read by that table like any other error, since the protocol does not say that a server that answers so has not acted (IFC-010, OPS-007). It is reached by `command`, `package` or `remote`, implements no operation of `runtime-provider.v1`, `machine-provider.v1` or `package-source.v1`, and learns its instance's configuration only through what its item's `environment`, `packageArguments` or `headers` take from it (PKG-020). An implementation that is not plain is one that carries Conduit's keys. A plain server reached by `remote` stands behind no gate and is reached as before, and a server reached by `remote` that cannot check an enforcement point's proof is used as plain (PKG-020, IFC-041). The word is used for nothing else: `interface.v1` and `pool.v1` are the core package's basic types. |
| gate | What stands before the server of a run that a runtime provider other than the engine's own runner makes, and before the server of an item reached by `remote` that is not plain: it lets a request reach the server only where the request carries proof, by the mechanism of DL13, that an enforcement point sent it, a credential that names the engine's credential ID in this version, in a form that no server that receives it can present to another, and nothing else on the server's machine reaches the server, root and, for a run, the operating-system user or group that the runtime provider uses there for its own means, which no run runs as or in, apart (PRV-025). Before the engine sends, what answers at a run's `url` proves by TLS, with the run's certificate, that it serves the instance (PRV-028). It is the server itself, something between the network and the server, such as a mutual TLS proxy beside it, or the runtime provider's own end of a channel to the run's machine that authenticates that machine and keeps what crosses it confidential and unaltered; a runtime provider's contract states its means (PRV-025). A network position, a value that is the same for every request, an end that admits a request without the proof, and loopback that other runs share are not gates (PRV-025). The engine checks who answers before it sends (IFC-017, IFC-041, PRV-028). No gate stands before what the engine reaches over stdio: the servers of the providers on its own runner and the processes of that runner (PRV-002, PRV-003). |
| implementation interface | The shared wire between an engine and an implementation, and between an engine and a consumer. It is the Model Context Protocol: an operation is one tool, and the engine presents to each consumer a server whose tools are the operations its open Conduits list (IFC-001, IFC-012). |
| the engine's address | The URL at which a consumer or a run reaches the engine's server, which a run is given as `CONDUIT_URL` in `identity` (PRV-022). It is not an address in the sense of a package's. A consumer on another machine reaches it at an `https` URL, whose canonical URI is the audience of the token of IFC-042. DL13 gives an `http` URL on loopback only to a run on the engine's own runner whose process ends when the engine stops, on an engine that can neither restart on another machine nor run as several parts, and every other run an `https` URL (DL13, PRV-022). A value that a runtime provider gives as the run sees it keeps the engine's address whole: its scheme, host, port and path (PRV-022). |
| baseline revision | The revision of the Model Context Protocol that every engine, and every implementation that carries Conduit's keys, supports. For this version it is 2026-07-28 (IFC-002). Either side may support others, and only a new version of this specification changes it (IFC-005). |
| Conduit's extension | The extension of the Model Context Protocol under which Conduit's keys travel, `io.github.shrav-k.conduit/implementation-interface`, with `revision` at `v0` for this version in its settings object. The settings object is the protocol's: the map with which a client declares an extension and a server lists it. The name `revision` is the protocol's too, which has an extension that makes a breaking change add or increment a `revision` string in its settings object. Before its first call to each run of an implementation that carries Conduit's keys, and to a `remote` item at each connection, the engine reads the implementation's result of `server/discover`, and it declares the extension on each call, for a request, a hook or a provider call; where the implementation does not list it, the request, the hook or the provider call is not dispatched and reports unavailable (IFC-037, PRV-005). The engine's own server lists the extension in its discovery result (IFC-038), and a request to the engine that carries any of Conduit's keys and does not declare the extension is answered with the protocol's error -32021 and reports invalid (IFC-036). An implementation that is sent a `revision` it does not support performs nothing and answers with the protocol's error -32021 (IFC-008), and one that carries Conduit's keys answers -32021 for a client capability that the call does not declare only where it has performed nothing, so either error from it gives the outcome failed (IFC-047, OPS-007); a plain server's -32021 is read as any other of its errors (IFC-010, IFC-045). A plain implementation is declared none. Beside the extension, a call declares no client capability but the tasks extension, where IFC-016 lets it (IFC-045). |
| Conduit's keys | The keys Conduit adds to `_meta`, each beginning `io.github.shrav-k.conduit/`, which travel as Conduit's extension (IFC-037). On a request that the engine sends to an implementation they are `instance`, `operation`, `invocation`, `caller`, `filters`, `config`, which is the instance's configuration, and `revision`, which is the instance's revision, with `idempotencyKey` and `conduit` where they apply (IFC-006); a provider call carries those that PRV-005 names. On a request that a consumer or an instance sends to the engine they are `idempotencyKey`, which a consumer may supply (IFC-023), and `serving`, on an onward request (IFC-020), and a request that carries one declares Conduit's extension (IFC-036). On a result they are `outcome`, or `reason` in its place (IFC-009, IFC-026); `restriction`, beside a reason that a restriction caused, whether an implementation gave the reason or the engine did (IFC-025, IFC-026); and, on a result that the engine returns to a consumer, `invocation`, the engine's ID for the invocation, where the request has an outcome or is a repeat that reports conflict (IFC-025). `reason` also stands in the `data` of the protocol's error with which the engine answers, at the baseline revision, a call to a tool it does not present (IFC-012), or a request of an instance that the protocol has it reject (IFC-036). In these keys a contract or an implementation of a submitted project is written `address#name` (IFC-018, SUB-008). |
| tool | A tool of the Model Context Protocol. An implementation that is reached by `command`, `package` or `remote` has one for each operation it implements (IFC-001). The engine presents one to a consumer for each operation of each of its open Conduits, other than `get-secret.v1` (IFC-012), and derives its definition from the Operation contract as the target holds it: its `inputSchema` and `outputSchema`, each a bundle, and for a control with each input that the target's template narrows given the `allOf` of the contract's schema and the template's; and `annotations` that hold `readOnlyHint` true only where the contract states no `effect`, is not a control and does not start model work, and the hints the contract states (IFC-033). It presents no tool for an operation whose contract the target's version of the package does not hold, nor for a control that the target does not have, because its type does not list it or its template's `controls` map leaves it out (IFC-033, IFC-012, TPL-013). A call that names a tool the engine does not present to the instance reports refused, or invalid where it names the tool that an open Conduit would give a control that the target does not have, where the target holds the control's contract (TPL-013), and is answered as the protocol prescribes for an unknown tool at the revision in use: at the baseline revision with the protocol's error and no tool result, and at a revision at which a tool result answers it, with one that carries the reason (IFC-012, IFC-025). When an instance's tools change, the engine notifies the streams that asked (IFC-038). |
| bundle (of a tool's schema) | The self-contained form of a tool's `inputSchema` or `outputSchema` that the engine presents, which can be read with no package at hand: it holds under the `$defs` of its root one copy of each Schema contract that the contract's schemas reach, directly or through other contracts, keyed by the contract's qualified reference, with `@` and the version of the package or project that holds it after the address where that package or project states one, so that no two packages, and no two versions of one, share a key; every `$ref` in it points to a copy, or to the same place within one, as the reference it was written as did; the keywords beside each `$ref` are kept; and a contract that refers to itself refers to its own copy (IFC-033). So a value is valid against it exactly where it is valid against the contract's own schemas (SCH-001, SCH-015). A contract whose schema holds no `$ref` may be written in the place of a reference to it beside which no keyword is written, instead of being copied. It follows the bundling of JSON Schema 2020-12, but a copy carries no `$id` and has its pointers rewritten instead, and neither the profile nor CTR-012 governs it ([schema-profile.md](schema-profile.md#schemas-this-profile-does-not-govern)). A trust bundle is something else, under its own row. |
| tool name | The name of a tool the engine presents to a consumer: the Conduit's local name and the operation's export name, joined by a dot (IFC-012). An export name ends in the contract's version segment, so a tool name does too, as in `checkout.directory.read.v1`. No two tools presented to one consumer share a name (IFC-014), and none is longer than the 128 characters that the protocol recommends, because a local name and an export name are each at most 63 (IFC-014). |
| local name | The name by which a consumer's tools name one of its Conduits. For a declared Conduit it is its key in the consumer's template. For a Conduit instantiated on its own it is `as`, or its own name where `as` is absent (IFC-012). It follows OBJ-022 and is unique among that consumer's Conduits that are not closed (IFC-014). |
| handle | A live value passed between operations, such as a running service. An input or an output of an Operation contract is one where it is a top-level property of the contract's `inputSchema` or `outputSchema` whose schema is the core schema `handle.v1` (CTR-002, IFC-011). On the wire it is an opaque string that its implementation issued, which the engine passes back unchanged and never interprets; a handle permits nothing (IFC-011). No instance holds one. |
| hold | Keep as part of what is stored for a template or an instance. An instance holds the resolved form of each of its references, its placement and its `runtime` among them (OBJ-009, PLC-001, PRV-006), and a template and an instance hold the versions and digests of their packages, or for the core package its address and version alone (NAM-009, PKG-005). Said of a map, a list or a document, the word means to have as a member: a declared Conduit holds `from`, and a record holds the caller. The word is not used for a Conduit or a right: an actor is the consumer of an open Conduit. |

## Providers

| Term | Meaning |
| --- | --- |
| provider | A Resource whose type offers one of the core package's four provider capabilities, and no other of them, and a secret Resource's type offers no other capability at all (PRV-001, SEC-022): a runtime provider, the machine provider, a package-source provider or a secret Resource. It has an owner and a placement, is made by registering its document and is set up as any Resource is. The server of a runtime provider, the machine provider or a package-source provider is run by the engine's own runner on `local` and reached over stdio, so it ends when the engine stops, or the part of it that holds the server stops, and after that the engine runs it again when it first needs to call it (PRV-002, PRV-026, DL17); a secret Resource is placed and run as any other Resource is (PRV-002), and where the engine's own runner runs it, its process ends as such a server does, and the engine runs it again before the first read through it (PRV-002, PRV-026). The engine's own runner, machine provider and fetching are part of the engine, and are no Resource and no provider in this sense (PRV-003). What a provider does is behind its capability, which any existing tool can implement; the user picks one by registering a Resource of its type, configured as it needs (PRV-001). |
| provider capability | One of the core package's capabilities `runtime-provider.v1`, `machine-provider.v1`, `package-source.v1` and `secret-provider.v1` (PRV-001). No Conduit permits an operation of the first three (PRV-004); a Conduit that lists the one operation of the fourth is opened only by the root Interface (SEC-008). |
| the engine's own runner, machine provider and fetching | The engine's built-in implementations of the first three provider capabilities, which serve where no provider of that kind does: its own runner runs an instance that names no `runtime`, as a process on the machine the engine runs on that it reaches over stdio, and ends failed the run of one placed on any other node (PRV-019), so such an instance that has an item that is run is placed only where `local`'s hostname label matches (PLC-007); it alone runs a `command` item whose program is a relative path (PRV-007); it passes the process, of the engine's environment, only `HOME`, `LOGNAME`, `PATH`, `SHELL`, `TERM` and `USER`, or on an operating system such as Windows those that DL16 names in their place, each only where its value does not begin with `()`, and the variables that a list set on it names, and what the item binds or `identity` gives wins over them (PRV-023, DL16); it is given without a call what `run.v1` would give, `identity` among it (PRV-003, PRV-022); it reaches each process over stdio, so no gate stands before it, and its processes run as the operating-system user that DL16 states, usually the engine's own, which is inside the domain of trust and can make the engine's proof (PRV-003, PRV-025, IFC-022); its own machine provider reports one machine, the one the engine runs on, which `local` represents, and places every instance there; and it fetches `https:` and `file:` URLs itself (PRV-003). They are part of the engine: no package provides them, they are no Resource, and no Conduit reaches them. |
| the list set on the engine's own runner | The names of the variables of the engine's environment that the engine's own runner passes to every process it starts, beside `HOME`, `LOGNAME`, `PATH`, `SHELL`, `TERM` and `USER`, as systemd's `PassEnvironment=` names those a unit passes. The user sets it, in a way that DL16 leaves to each engine (PRV-023, DL16). A variable it names reaches every such process, outside every Conduit; the runner passes no other variable of the engine's environment, the six apart, and what the item binds takes its value from the instance's configuration and wins, as a variable of `identity` does (PRV-023, SEC-020). A process that runs as the engine's operating-system user may still read the engine's own environment where the kernel admits it, so a token belongs in a store (PRV-023). No other runtime provider has it: what else a run receives from where it runs is that provider's (SEC-020). |
| runtime provider | A provider whose type offers `runtime-provider.v1`: it runs an instance's item that is run, on the machine that `run.v1` gives in `machine`, which is that of the instance's node, or not at all, stops it and reports its state (PRV-007 to PRV-009, PRV-019). Its contract states which registry types and transports of a `package` item it runs, a `stdio` one only bridged behind its gate (PRV-012), where it keeps the values of secrets it is given and the channel over which it carries them to another machine (PRV-011), its gate (PRV-025), whose end at the run's `url` proves with the run's certificate that it serves the instance (PRV-028), and whether it confines what it runs (ACC-027). It is also the route for confining an Agent's own tools, with the limits in its contract and configuration (PRV-006); this version reports their reach as neither enforced nor mediated (CTR-014). It delivers the variables and the files of a run's `identity`, and carries and keeps them as it does a secret's value (PRV-022), and its contract states what it does with a stop that it cannot carry out now, such as carry it out once it can, and where it keeps that stop so that neither a restart of the engine nor its own retirement loses it, which through its retirement takes something that runs without its server, such as its part on the run's machine (PRV-021). Its calls of `stop.v1` and `inspect-run.v1` give it the run's machine as `run.v1` does (PRV-027). Several may exist, owned by any Pool (PRV-013); one is not retired while an instance that exists names it (PRV-020), and no instance names one that is retired (PRV-006). It is itself placed on `local` and run by the engine's own runner (PRV-002), which runs it again after the engine restarts, or the part of it that held that run stops, when the engine first needs it (PRV-026). |
| `runtime` | The standard argument by which an Agent or a Resource names its runtime provider: a reference to a Resource whose type offers `runtime-provider.v1`, held in the resolved form for the instance's whole life, and changed by no operation, as a Pod names its `runtimeClassName` (PRV-006). An instance that is given none runs on the engine's own runner, which runs only on the machine that `local` represents (PRV-003, PRV-019), so where an item that is run is selected for it, its label selector also holds `local`'s hostname label (PLC-007). A template gives none, and one that names a retired runtime provider makes the document that gives it rejected (PLC-005, PRV-006). The Resource of a Pool's entry takes it only from an input of the Pool's template, which states no `default` for it (POOL-009, PLC-005). |
| run | The running of an instance's item that is run, by its runtime provider, which the engine asks for with `run.v1` in a setup, or in a retirement to serve its retire hook where that hook is to be dispatched, where the provider reports it `stopped`; where it reports `unknown`, no run is asked for (PRV-007, TPL-018). It runs on the machine of the instance's node, or the run ends failed (PRV-019). It is named by the instance's ID alone, so one run serves one instance (PRV-007). The engine gives it, each as a string and by name, the values that the item's `packageArguments` and `environment` take from the configuration, a place that holds null giving none; the secrets read for it apart, in `secrets`, under `environment` and `packageArguments`; in `identity`, what the mechanism of DL13 gives it to reach the engine and present itself; and, in `machine`, the hostname and labels of the machine of the instance's node (PRV-007, PRV-022). The engine reaches the server at the `url` the run returns, a Streamable HTTP URL that every runtime provider returns, or at the latest that `inspect-run.v1` reports, behind the runtime provider's gate and once what answers there has proved by TLS, with the run's certificate, that it serves the instance; or over stdio on its own runner (PRV-007, PRV-025, PRV-028, IFC-017). It is stopped with `stop.v1` in a retirement, and once more when its instance is unregistered (PRV-008, LIF-036), its state is read with `inspect-run.v1` and reported as the condition `Running` (PRV-009), each call giving the run's machine (PRV-027), and its runtime provider may restart it under its own restart policy (PRV-010). No instance holds a run. |
| `identity` | The input of `run.v1` that carries what a run needs to reach the engine's server, present itself as its instance and, behind a gate, check the engine's proof and prove who answers, under names fixed for every engine and no other, which [names.yaml](names.yaml) holds (PRV-022): under `environment`, `CONDUIT_URL`, the engine's address, and `CONDUIT_IDENTITY_DIR`, a directory; and under `files`, keyed by their paths in that directory, which are their names, the trust bundle, `ca.crt` and `jwks.json`; `engine-id`, the engine's credential ID; `token`, a signed token in the form of a JWT-SVID; and `tls.crt` and `tls.key`, a certificate in the form of an X509-SVID and its private key, where the mechanism uses mutual TLS for the run or the run's server stands behind a gate. Every run is given every file but those two, which the schema of `run.v1` requires (PRV-007, PRV-022). The mechanism of DL13 fills it, and a credential in it names the instance by its ID and lasts as long as the instance: nothing renews it in this version (PRV-022, DL13). The runtime provider delivers it to the run, carries it to another machine only over a channel that authenticates that machine and keeps it confidential, puts it nowhere else but the run's gate, and keeps it as it keeps a secret's value, and gives each variable in place of any other value it would take, such as a default of the item's Package; and no record, inspection result, observation, diagnostic or result holds it (PRV-007, PRV-011, PRV-022, PRV-024, IFC-022). No template selects an item that binds either variable, in any case of its letters (MAN-018), and the engine's own runner passes no variable of the engine's environment in its place (PRV-023). The engine's own runner is given it without a call, and delivers it in the same way (PRV-003). It is not an idempotency key. |
| trust bundle | The files `ca.crt` and `jwks.json` of `identity`, as a SPIFFE trust bundle holds its X.509 and its JWT authorities: in `ca.crt`, in PEM, the root certificates from which the mechanism of DL13 issues every credential, and those from which the certificate at the engine's address is issued where they are others, such as a public certification authority's, with which a run checks who answers at the engine's address and a gate checks the engine's certificate, as a Kubernetes Pod is given the root certificate of its cluster; and in `jwks.json`, the JWK Set of the keys that check a token that the mechanism signs, with which a gate checks the engine's token (PRV-022, DL13). The engine keeps each root and each key for as long as a run that holds it lasts (DL13). |
| credential | What a sender presents to prove who it is. In the promises on who is who it is what the mechanism of DL13 issues from its one root of trust, in one of its two forms: a certificate and its private key in the form of an X509-SVID, for mutual TLS, or a signed token in the form of a JWT-SVID (DL13). A run's credential is given in `identity`, names its instance by the instance's ID and lasts as long as the instance, since nothing renews it in this version and the time at which it lapses is set so far ahead that it does not lapse while the instance exists; once the instance is removed it establishes no instance, even where another instance has taken its name, because the engine checks on every request that the instance it names still exists (PRV-022, IFC-022, IFC-032). The engine presents its own as an enforcement point, naming the engine's credential ID, which the mechanism issues to the engine alone, and it may be short-lived (DL13, PRV-025). The word keeps its ordinary sense elsewhere, such as the credential with which a package's archive is fetched, which comes from the scheme's own mechanism and never from a `fetch` (MAN-006). |
| enrollment | One root-opened attempt to join a managed machine through a provider, with ID, provider Resource, bound labels, expiry, require and headless and weaker-check flags (ENR-001). A join is pending until root admits it; closing, refusing or expiry never authorizes later admission. |
| admit | Accept a pending machine through its open enrollment after ENR-006's checks, by admit-machine.v1. On provider acceptance the engine makes its node; no Conduit or credential follows (ENR-007, ENR-011). |
| refuse (a machine) | Root's refuse-machine.v1 closes an enrollment or asks its provider to remove unrepresented machines. It also answers a retired node's removal question (ENR-008, ENR-012). It is an operation; refused as a request's reason has its separate meaning. |
| pending (a machine) | Joined but not admitted: the provider reports pending, no node represents it and no instance is placed on it (ENR-004). Distinct from a pending action and from shutdown: pending. |
| evidence, evidence item | What the engine observed or an implementation or provider reported through a call, never a model's turn. Each evidence-item.v1 holds kind, value, where and proves (PND-004). Enrollment needs fingerprint or attestation and, except the recorded headless exception, an exact comparison with the person's typed fingerprint (ENR-005, ENR-006). Pending machine evidence is panel-only at root and recorded with the answer (PND-008). |
| machine ID | The provider's required opaque stable id, scoped to its Resource and derived from the machine's key where offered (ENR-002). It is no object ID and is not governed by id.v1; admission binds it with provider and hostname (PLC-026). |
| machine | A computer the machine provider reports with list-machines.v1, identified by its required provider-scoped opaque id and canonical hostname, labels and state: pending, reachable, unreachable or gone (PRV-014). A report names each id and hostname once. A pending machine is no object, is no pending action's subject, has no node and is never a placement (ENR-004). Only admission makes a node, apart from local at first start (PLC-026). |
| machine provider | The provider whose Type offers machine-provider.v1: it reports machines, places an instance given no placement, and serves enrollment, acceptance and removal (PRV-014, PRV-015, ENR-002, ENR-007, ENR-008). At most one that is not retired exists, owned by system (PRV-013). With none, the engine's own provider serves local only and enrolls nothing (PRV-003). Retiring or replacing it closes its open enrollments and leaves non-local nodes omitted until new enrollment, without retiring or rebinding them (PLC-026). Report timing and maximum enrollment duration are DL5. |
| label | A key with a string value, as Kubernetes labels a Node. The three descriptive labels are kubernetes.io/hostname, kubernetes.io/os and kubernetes.io/arch; the last two use Go's GOOS and GOARCH values (PRV-014). A node's labels are fixed when made: the three reported values plus only the enrollment's labels, or local's labels configured at first start (ENR-010, DL6). The provider binds the enrollment's labels; no later report changes a node's labels. Labels are held in status; the enrollment is the narrow exception to no document or operation setting one. A label is not a name (OBJ-022). NAM-001 alone also uses label in RFC 1123's hostname sense. |
| label selector | A map from a label to a value, written as `nodeSelector` in a Type contract or an implementation item, as a Kubernetes `nodeSelector` is, with the core schema `labels.v1` (CTR-004, MAN-010), and given to `place.v1` in its input `nodeSelector` (PRV-015). It is matched against the fixed labels that the node's status holds (PLC-007, PLC-026, ENR-010). An instance is not instantiated on a node whose labels do not hold each label of its type's selector and of every selected item's, and, where an item that is run is selected for it and it names no `runtime`, `kubernetes.io/hostname` with the value in `local`'s status, each with the value given (PLC-007); a template whose item's selector gives a label another value than its type's or another selected item's is rejected (PLC-025). A selector that is left out or empty puts no rule on where an instance is placed (CTR-004, PKG-019). |
| package-source provider | A provider whose type offers `package-source.v1`: it fetches a package's archive, with `fetch-package.v1`, for a `fetch` whose URI scheme it claims (PRV-017). Its type's `schema` requires `schemes`, and it claims the schemes that its configuration lists there, compared without regard to case (PRV-016). Its type lists no control whose `changes` holds the pointer to the whole configuration, `/schemes` or a pointer within it, so the schemes it claims are fixed for its life: a provider that is to claim other schemes is another instance, registered once no provider that is not retired claims them (PRV-016, PRV-013). For each scheme at most one that is not retired exists, owned by `system` (PRV-013). Where none claims `https` or `file`, the engine fetches the archive itself (PRV-003, PRV-017). |
| provider call | The engine's call of an operation of `runtime-provider.v1`, `machine-provider.v1` or `package-source.v1` of a provider, which begins no invocation. It is not a request: no Conduit permits it, no access decision is made for it and no restriction applies to it. It carries the provider's own `instance`, `config` and `revision`, and `operation`; where it is made within an invocation, that invocation's ID; and where it is made for a request, that request's caller. It declares Conduit's extension, and its result is read as a request's (PRV-005, IFC-037). It is recorded: its record holds in `invocation` the invocation within which it is made, and a call of `run.v1`, `stop.v1` or `inspect-run.v1` names in `subject` the instance whose run it is (PRV-005, REC-001, REC-002). enroll.v1, accept-machine.v1 and remove-machine.v1 are within root's enrollment invocations, with no action in records (PRV-005, ENR-003). The read of a secret is a request, and not a provider call. A provider call is carried by a call, which the Model Context Protocol calls a request, as it calls any JSON-RPC request. |
| user | The person who runs an engine and picks its providers, by registering Resources of their types (PRV-001), and who may name a mirror for packages (NAM-012). The word names no object and no actor: what the user registers is decided through Conduits, as any registration is. |

## Secrets

The limit of what the promises on secrets guarantee is stated in
[spec/README.md](README.md#what-the-guarantee-for-secrets-covers), as a statement and not a
promise.

| Term | Meaning |
| --- | --- |
| secret Resource | A Resource whose type offers the core capability `secret-provider.v1`, whatever store its type reads (SEC-002). Each kind of store is its own Type, whose `schema` states the form of the locator and which lists no control (SEC-005), and which offers no other capability (SEC-022): a store package that lists or writes secrets does so through another Type, whose Resources are not secret Resources. A secret Resource is placed and run as any other Resource is (PRV-002); where the engine's own runner ran it and its process ended with the engine, the engine runs it again before the first read through it (PRV-026); and its server, where a runtime provider other than the engine's own runner runs it or it is reached by `remote` and is not plain, stands behind a gate, so that only an enforcement point reaches it (PRV-025, SEC-006). Its implementation of `get-secret.v1` reads the store that its locator names (SEC-006). Each secret Resource locates exactly one secret, so `get-secret.v1` takes no input, where the `GetSecret` of External Secrets Operator or Dapr, whose store serves many secrets, takes the name of one (SEC-005). |
| store | The system outside the engine that holds a secret's value, such as a keychain, a vault or a file, which a secret Resource's locator names (SEC-006). No store is built into the engine: each is reached by a package's implementation of `get-secret.v1` (SEC-020). What a store needs from where it runs, and its own forms of versions, keys and caching, are its package's contract. |
| locator | The configuration of a secret Resource, which names where its store holds the value, in the form that the `schema` of its type states (SEC-005, SEC-006). Its type lists no control, so it is fixed once the Resource is made (SEC-005). |
| secret reference | A value at a place that the core reference schema `secret-reference.v1` governs: a reference to a secret Resource, never the secret itself (SEC-001, SEC-002). A literal or a bare name at such a place makes the document that holds it rejected (SEC-001), and neither a diagnostic nor a record holds what was written there, other than a reference in its resolved form (SEC-003, SEC-004). An implementation item binds a variable, an argument or a header to such a place, and the engine reads the secret for it (SEC-010, SEC-013). |
| the engine's read of a secret | The engine's request for `get-secret.v1` for an instance, through that instance's own open Conduit to the secret Resource: before each run it asks for, for each secret that the item's `environment` or `packageArguments` points to (SEC-010); before it connects to a `remote` item, in a setup or in a retirement to serve its retire hook, for each secret its `headers` points to (SEC-013); again where the engine has lost the values of a connection that lasts, as after it restarts, for each secret Resource that the setup which made the connection read (SEC-023); and, once the engine has restarted, or the part of it that held a provider's run has stopped, before it runs again a provider whose run ended with it (PRV-026). It is the only request for `get-secret.v1` that is dispatched: an instance's request for it is refused, and no tool is presented for it (SEC-007, IFC-012). It belongs to the setup or the retirement within which the run or the connection is asked for, has its caller, and is decided by that Conduit and its filters alone (SEC-011); a read again belongs to the setup that made the connection, and a read for a provider's run made again to the setup that last asked for that run, although that setup may have ended, and each is decided by the Conduit and its filters as they stand when it is made (SEC-023, PRV-026, SEC-011). It is recorded without its value (SEC-015), the engine keeps no copy (SEC-017), and the value goes only into the run's `secrets` or the header (SEC-018). A read that does not succeed stops the run or the connection, and a request to the instance's implementation reports unavailable (SEC-012). The promises also say "a read". |
| domain of trust (of a secret) | What can read a secret once the engine has read it: the machine the engine runs on and its operating-system user, every program that runs as that user among them, the processes of the engine's own runner too where they run as that user (IFC-022, DL16); the place where the runtime provider keeps a run's values, and the run's machine and its gate, for what that run serves (PRV-011); and where the signing keys of DL13 are held (DL13), as the Secrets Manager agent of AWS calls the places where its endpoint and its token can be reached. It is not SPIFFE's trust domain, a namespace of identities, which a mechanism of DL13 may use. [spec/README.md](README.md#what-the-guarantee-for-secrets-covers) states what that leaves open. |

## Lifecycle

| Term | Meaning |
| --- | --- |
| lifecycle state | One of registered, ready and retired. Every instance of every family has exactly one, and it only moves forward (LIF-001, LIF-006). A template has none (LIF-012). |
| registered | The state an instance has when it is instantiated (LIF-002), and keeps until its setup succeeds or it is retired. As a description of an object the word names only this state. |
| ready | The state of an instance whose setup has succeeded (LIF-003). A Conduit that is ready is open. It is a lifecycle state, a phase in Kubernetes' terms, and neither the Kubernetes condition `Ready` nor CRI's `RuntimeReady`. It does not change when the run stops or the machine becomes unreachable, and "not ready" means registered or retired (LIF-010, LIF-011). Conditions report health (LIF-011, PRV-009). |
| retired | The state of an instance from the moment a request to retire it is dispatched, whatever the outcome (LIF-005). It is never brought back (LIF-006). A retired instance still exists until it is removed: once its shutdown is confirmed (LIF-035), or by a request to unregister it (LIF-017, LIF-007). |
| set up | Carry out the setup of an instance, which is one invocation of `set-up.v1`, requested of the target ACC-033 names with the instance as its input `instance`, and which the engine implements (TPL-008). Its parts are, in order: the opening of its declared Conduits or, for a Pool, the setting up of the Resources of its entries; then the run of its item that is run and the connection to each of its `remote` items; then, where its Type states signIn and its account pointer holds a string, the account check and any undo under PND-005 and PND-011; then its setup hook (TPL-012, CON-004, POOL-013, PRV-007, IFC-041, TPL-017). A part is begun only once every earlier part that is not optional has succeeded; the run and the connections stand at one position in the order, and none waits for another; and no part is begun once the instance is retired or the setup is cancelled (TPL-012). A further setup leaves an open Conduit, a ready Resource and a running run as they are, and dispatches the hook again only as its idempotency key allows (TPL-012, OPS-028). A setup that does not succeed closes no Conduit it opened, retires nothing it set up and stops no run it asked for (LIF-027). The noun is setup. For a Conduit the verb is open. |
| part | One of what a setup, a retirement or sign-in.v1 does: the opening of one declared Conduit, the setup of one entry's Resource, the run, the connection to a `remote` item, a hook, or the stop of the run (TPL-012, TPL-009, TPL-018). A part that opens a declared Conduit or sets up an entry's Resource is under that one's name (CON-004, POOL-013). The outcome of a setup or a retirement is counted from its parts (OPS-022). A part of the engine is something else: one of the several parts, on one machine or several, of which an engine may be made where its conformance document says so (DL17, engine). The promises write it "a part of the engine", or "the part of it" where "it" is the engine, and say that an engine "runs as several parts". A part that reports a reason or ends with an outcome belongs to a setup, a retirement or sign-in.v1. |
| retire | End an instance for good, by its retirement, which is one invocation of `retire.v1`, requested of the target ACC-033 names with the instance as its input `instance`, and which the engine implements (TPL-008). Its parts are: where a setup of it was ever dispatched, its retire hook, where its template selects one, and then the stop of its run, where an item that is run is selected for it (TPL-009, TPL-018, PRV-008). An instance whose shutdown is not confirmed may be retired again (LIF-026); one whose shutdown is confirmed has been removed (LIF-035). The noun is retirement. For a Conduit the verb is close. |
| shutdown | The stopping and releasing of what a retired instance itself holds, as its type contract defines, and the stop of its run (LIF-016, PRV-008). The status reports it as confirmed, pending or unknown (LIF-014). It is confirmed once an invocation of `retire.v1` for the instance has succeeded, or a reconciliation has recorded one as having occurred, at once for an instance for which no setup was ever dispatched, and for a Conduit when it is closed; it is unknown where the outcome of the latest retirement is unknown, and where a setup was dispatched and the instance's node was declared lost or its machine reported gone; and it is pending otherwise (LIF-024). An instance whose shutdown is confirmed is removed at once (LIF-035), so confirmed is seen in the result and the record of what confirmed it. |
| remove | End an instance's existence. The engine removes a retired instance once its shutdown is confirmed, with no request, and a Conduit when it is closed (LIF-035); a request to unregister removes a retired instance, asserting that its shutdown is settled in another way, after asking its runtime provider once more for the stop of its run (LIF-017, LIF-036). Its removal is not a retirement and is recorded (LIF-035, REC-001). A removed instance no longer exists: its records are kept, its name can be given to another object, against which a lifecycle action that expects the removed instance's ID reports conflict (LIF-037), objects that referred to it keep its ID and report it as missing, and a request that names it reports invalid (LIF-019, OBJ-002, OPS-029). |
| declare lost | Retire a node and every instance placed on it, without their shutdown being confirmed; PLC-017 says what the status of each then reports. The root Interface does it with `declare-lost.v1`, an operation reserved to it, whose input `node` names the node: a node that a request has already retired is declared lost in the same way, and a second request for one node changes nothing and succeeds (PLC-017). The engine declares a node lost itself, with the same effect and with no request, when the machine provider reports its machine gone (PLC-024). |
| unregister | Remove a template, which then no longer exists (LIF-012); or remove a retired instance (LIF-017), whatever comes of the stop that it asks once more of the instance's runtime provider (LIF-036). A request to unregister any other instance reports conflict (LIF-017). Records are kept, and objects that referred to what was unregistered keep its ID and report it as missing (LIF-019). How records that name no object that still exists are read is left to each engine, as item DL8 of the implementation-defined list. |

## Inspection, observation and records

| Term | Meaning |
| --- | --- |
| inspect | Read an object. For an instance the result holds what was declared, the status, and the records about it, and, for an instance other than a Conduit, its inventory (LIF-013). `inspect.v1` returns these as `declared`, `status`, `records` and, where applicable, `inventory`. Inspecting an Interface or an Agent also shows its scope, and inspecting a Pool shows its administrators with their Conduits (LIF-013). These outputs stand beside the object's `id`, `revision` and `packages`, a list of items that hold `address`, `version` and `digest`, or for a submitted project its address, its version where its manifest states one and the digest that identifies its contracts (NAM-009). A reference in what was declared is shown in its resolved form. Inspecting a Conduit reports, for each restriction on it, enforced or mediated (ACC-027), and inspecting an open Conduit names, under each requirement it applies, the implementation that applies it: the engine for a requirement of the core package, and otherwise by its qualified reference, `address#name` for an implementation of a submitted project (ACC-038). The status of an instance lists in `unreconciled` the engine's ID for each invocation whose outcome is unknown and that was dispatched to it or names it (LIF-013). Inspecting has no effect and gives no access (OBS-006). Pending visibility is limited to Interfaces at which the action is raised (PND-002). |
| declared | Said of the part of an inspection result that is the instance's resolved definition and configuration. It changes only by an operation that an actor requested, never because of an observation (OBS-001). |
| status | The part of an inspection result that the engine writes: the lifecycle state, the shutdown of a retired instance, the conditions, and `unreconciled` (LIF-013, LIF-014, LIF-011); for a node, also fixed labels and, after admission, machine {provider, id, hostname} and enrollment (PLC-008, PLC-026, ENR-010); and what the promises have it report besides: how a setup that did not succeed ended (LIF-004), what retired a retired instance (LIF-005), each Conduit of which the instance is the consumer that was closed while it is ready (CON-011), and why its shutdown is unknown where its node was declared lost or its machine reported gone (PLC-017, PLC-024). A submitted document may not carry it (OBJ-004). An Interface raised an action also sees it in the subject's status.pending (PND-002). |
| `unreconciled` | The member of an instance's status that lists the engine's ID for each invocation whose outcome is unknown, that was dispatched to the instance, its hooks among them, or that names it in an input or as its target, its setups and retirements among them (LIF-013). It is read from the engine's own state, so no purge shortens it, and an actor finds there an invocation to reconcile whose ID it never held or has lost (OPS-008, OPS-014, REC-004). An invocation leaves it once it is reconciled. |
| condition | A further state of an instance, reported in `conditions` in its status, in the shape of Kubernetes `metav1.Condition`, without its optional `observedGeneration`, with `lastHeartbeatTime` and `source` added as Conduit's own, as the core schema `condition.v1` gives it (LIF-011). A type's contract names the conditions it reports, such as running, paused or idle (CTR-004), and the engine reports the condition `Running` of an instance whose item is run (PRV-009). A condition never changes the lifecycle state (LIF-011). |
| observation | Something seen of an instance, reported as a condition with the time of the last successful observation in `lastHeartbeatTime` and its source in `source` (OBS-002). What cannot be observed now is reported as unknown, a condition whose `status` is `Unknown` (OBS-003). A difference from what was declared is reported, and is not removed without a request (OBS-004). |
| source | The context in which a record or an observation was made, such as one node or one runtime provider (PRV-009): CloudEvents' attribute `source`, a URI-reference that the engine names, which a record holds as its CloudEvent's `source` and a condition in its member `source` (REC-005, OBS-002). Records are in order within one source, and no order is promised between sources, so an engine that names one source for every record keeps them all in one order (REC-005). The core package's capability `package-source.v1` and its package-source providers are another thing. |
| record | What is kept about a request, a provider call or another occurrence: who, what, when and how it ended (REC-002). Its form is the core schema `record.v1`, a CloudEvent whose `data` holds those fields; `inspect.v1` returns records in that form, and an engine may also export them in it (REC-002, DL8). REC-001 lists what is always recorded. Its `invocation` is the ID that the recorded call carried, the request's, the hook's or the read's own, and for a provider call the invocation it was made within; `serving` names the invocation that it serves, where it serves one; a record of `run.v1`, `stop.v1` or `inspect-run.v1` names in `subject` the instance whose run it is; and the record of a change that no request asked for, such as a Conduit closed under CON-008, holds the invocation within which it happened, or states the cause where there is none (REC-002). A record is added and never altered, and only a purge removes one (REC-003). Whether it keeps the inputs and the outputs of an operation is stated by `records` in the type's contract (CTR-004, REC-002); a record holds no secret (SEC-004, SEC-015). As a noun in the promises the word is used for nothing else: what the engine keeps for repeats and reconciliations is its own state (OPS-008). |
| purge | Remove the records made before a time the request names. It is an operation reserved to the root Interface, `purge.v1`, and itself leaves a record (REC-004). It removes records and nothing else: what repeats and reconciliations need is the engine's own state, which no purge touches (OPS-008), so an invocation of unknown outcome is still found in the status of its instance (REC-004, LIF-013). |
| unknown | The one word for "cannot tell": for an outcome, for an observation, for a shutdown and for a setting that a control addressed. It is never a lifecycle state (LIF-001). |

## Configuration and change

| Term | Meaning |
| --- | --- |
| definition | What a template or an instance declares apart from its configuration: its type, its `implementation` map, its controls and its nested instantiations, and for a Conduit its capability, operations and requirements. An instance's definition is resolved when the instance is made (INS-013), and no control changes it. The definition of a tool is something else: what the Model Context Protocol calls a tool's definition, which the engine derives from the Operation contract (IFC-033). |
| configuration | The stored settings of an instance. It is the value written under `config`, which the `schema` of the instance's type governs (CTR-004): a template writes it in its `spec`, or writes none and so has an empty one (INS-024), inputs fill it when the template is instantiated, and afterwards controls change it. `config` is where configuration is written, and a setting is one place in it. The engine sends an instance's configuration, as stored, with every call for a request or a hook to an implementation that carries Conduit's keys (IFC-006), and a secret appears in it only as its reference (SEC-018). A node's configuration is empty (PLC-008), and a secret Resource's is its locator (SEC-006). No control changes a locator, or the `schemes` of a package-source provider (SEC-005, PRV-016). |
| control | An operation whose Operation contract also states, under `changes`, the settings it changes: a map from the name of an input to the pointer of the setting that input sets, in which no two pointers are equal or lie one inside the other, so that each setting is set by one input alone (CTR-006, OPS-020). A type lists its controls, and a template chooses which of them its instances have and may narrow their inputs (TPL-010); the tool that the engine presents for a control shows the narrowing of the target's template, and none is presented for a control that the target does not have (IFC-033, IFC-012). It is requested through an open Conduit to the instance whose configuration it changes. Its contract's `inputSchema` requires `revision`, it declares no output `settings` (CTR-006), and the root of each of its schemas holds only `type`, `properties`, `required` and `additionalProperties` (CTR-012). The type of a secret Resource lists none (SEC-005), and that of a package-source provider none whose `changes` reaches its `schemes` (PRV-016). `revision` is the one input it must always be given (REV-006). It applies exactly the values it was sent, or fails, and on success exactly those are stored at the pointers of its `changes`, unless its instance was retired while it ran (REV-007); one whose values would make the configuration fail the type's schema is not dispatched and reports invalid (REV-015). The settings a control addressed are those of the inputs it was sent (REV-009). The core package has none. |
| revision | The single value on a template or an instance that a change is checked against (REV-001). It is an opaque non-empty string, compared only for equality, as an HTTP entity tag is (REV-001). A request to change an object names the object's current revision, in the operation's input `revision` (REV-002, REV-011). The revision advances exactly when the stored definition or configuration changes, and never returns to an earlier value (REV-003 to REV-005). Setups, retirements and changes of one instance are applied one at a time, and one that arrives while another has not ended reports conflict (REV-012, REV-014), while the engine's own retirements under PLC-017 and PLC-024, and its closings under CON-008, take effect at once (REV-012); setting up and retiring name no revision and advance none (REV-012). The key `revision` of Conduit's keys holds an instance's revision (IFC-006); `revision` in the settings object of Conduit's extension is something else, the extension's version (IFC-037). |

## Packages

| Term | Meaning |
| --- | --- |
| package | What an author ships: a manifest and the things it exports, distributed as one archive, which is a gzip-compressed tar file with the manifest at its root (PKG-022, MAN-013). It is identified by its address, and each release of it has a version. A package is a project that has been published, and its manifest states its own address and version (PKG-017). It holds templates and contracts only: one that holds an instance document is rejected when it is installed (MAN-011). |
| address | A package's identity, or a submitted project's: a host part, which is a lowercase DNS name with a dot in it, no port and no trailing dot, and then a path, which an address may lack, such as `github.com/acme/conduit-history` (NAM-001). A release that breaks with those before it should take a new address (NAM-025). A submitted project that holds a contract or lists an implementation states one too, which may not be that of an installed package (MAN-015, MAN-016). The engine's address is a URL, under its own row, and the address that a request came from, in PRV-018, is a network address. |
| version | Of a package: a Semantic Versioning 2.0.0 version (PKG-001). A release is one version of a package. Two versions are the same when neither precedes the other (PKG-003). A manifest names exactly one version of each package (NAM-006), and a reference never carries one (NAM-005). |
| manifest | The one file of a project that lists the packages it uses, named `conduit.yaml`, `conduit.yml` or `conduit.json` (MAN-001); a project that has more than one of them is rejected (MAN-002). It carries `apiVersion` and is not one of the ten kinds of document: it has no `kind`, `metadata` or `spec` (MAN-003). Its other keys are `packages`, `exports`, `implementations`, `address` and `version`, and it states `version` only beside `address` (MAN-004). A package's manifest states both (PKG-017), and a submitted project's states `address` where the project holds a contract or lists an implementation (MAN-015). `packages` is a map keyed by address, and each item gives exactly one `version`, that version's `digest`, and optionally `fetch` (NAM-006, MAN-005). `exports` is a list of the names of the package's own documents (PKG-018, MAN-007), and `implementations` is a map keyed by name (PKG-019, MAN-009). |
| `fetch` | The key of an item of `packages` that gives the place to fetch the package's archive from. Its value is a URI reference, which holds no user information (MAN-006). A relative one is resolved against the directory the manifest was read from, to a `file:` URL, and is rejected where the manifest was handed over without a directory (MAN-006). Every engine accepts a `fetch` whose scheme is `https` or `file`, and one of another scheme only where a package-source provider claims it (NAM-012, PRV-017). The package is still identified by its address. |
| user information | The part of a URI where RFC 3986 places a credential. A `fetch` holds none: a credential comes from the scheme's own mechanism (MAN-006, NAM-012, PKG-023). |
| export | Something in a package that the package's manifest names so that others may refer to it: a document, which is a template or a contract, listed in `exports`, or an implementation, exported by its item under `implementations` (PKG-018, PKG-019, MAN-007). A package exports only its own documents. From outside the package it is reached only by a qualified reference. Its name is made of segments separated by dots and is at most 63 characters long (NAM-004). |
| core package | The package built into every engine, at the address `github.com/shrav-k/conduit/core`. It is written out as documents under [core/](core/README.md) and [schemas/](schemas/README.md). It exports the Operation contracts of the management verbs, of the setup and retire hooks and the three sign-in hooks, of the operations of the provider capabilities and of `get-secret.v1`; the capabilities that `management`, `access` and a Pool offer, and the four provider capabilities; the basic Interface and Pool types and the types of a node, of `management` and of `access`; the requirements `bound.v1` and `shared-host.v1`; the reference schemas, the schemas of documents and the schemas of an object as a result names it, a diagnostic, a handle, a condition and a record; and the templates of the first-start objects and of the two Conduits of `root` (OPS-019, ACC-029, OBJ-021, PRV-001, FST-005). Its one implementation, `engine`, is the engine itself, and implements no operation of a provider capability (MAN-012). It needs no item of `packages` in any manifest and cannot be replaced (NAM-020, NAM-021), and it has no digest. |
| the contracts of a submitted project | What the engine makes available of a submitted project's contract documents and of the implementations its manifest lists, and in the same way of the project handed over with a template that replaces another (SUB-009): to the project's own documents as `#name`, and elsewhere, on the wire and in a bound, as `address#name`, with the address its manifest states (SUB-008, MAN-015). They are not registered. The engine identifies those of each submission by a digest: the SHA-256 of the RFC 8785 form of one map that holds `documents`, the project's contract documents ordered by kind and then by name, each compared by the bytes of its UTF-8 string, and `manifest`, the manifest as it was handed over, before any relative `fetch` or program path is resolved (SUB-008). A template registered or replaced with them keeps the address, the version where the manifest states one and that digest, as it keeps the version and digest of any package (NAM-009, SUB-009). |
| selection | A document's choice of a type, a capability, an operation, a requirement or an implementation, written as a qualified reference or in the `#name` form (NAM-018). The `from` of an instance names a template and is not a selection (INS-025). A selection that names nothing, where the package it names is installed or the project is its own, makes the document that holds it rejected (NAM-028). The keys of an `implementation`, `controls` or `tools` map are selections of operations (TPL-003, TPL-010, PKG-020). Implementations are selected in the one `implementation` map of a template's `spec`, keyed by operation, the setup hook and the retire hook among them. An operation that is not a key there takes the default its type states; an Operation contract states none (CTR-002). An operation that the core package's implementation `engine` lists is implemented by the engine as a rule, and is not a key of any template's or type's map (TPL-003, TPL-004). |
| digest | Of a package: the SHA-256 of its archive file exactly as distributed, written as `sha256:` followed by the hash in lowercase hexadecimal (PKG-004, PKG-022). The core package has none (MAN-012). A `package` item states no digest of its own: its Package is pinned by server.json's `fileSha256`, the hash alone in lowercase hexadecimal, or, for an `oci` image, by a digest written `@sha256:` and the hash at the end of its `identifier` (MAN-010). The digest that identifies the contracts of a submission is the one SUB-008 defines. |
| contract | A document of the kind `Type`, `Capability`, `Operation`, `Requirement` or `Schema`, which states what a type, a capability, an operation, a requirement or a schema is (CTR-001). Its name is its export name, and the last segment of the name, written `v` and a whole number from 1 as in `.v1`, is its compatibility version, with at least one segment before it (CTR-001): two names that differ only there are two contracts (NAM-015). Under one name a later release may only add optional things, and an input that it adds to a Requirement states no `default` (NAM-024). A contract is not registered. A type's, a provider's or a package's contract also names the prose published beside it, under its own row. A property added at any depth of a published Type's schema states no default under the same contract name; a default takes a new version segment (NAM-024). |
| a type's contract, type contract, a provider's contract, a package's contract | The Type contract of the type, or the contracts of the package, together with the prose that the package publishes beside them about how what it provides behaves, which no engine reads. Where a promise says that such a contract states something that no key of a contract document holds, it means this prose: what a type's further conditions mean (CTR-004), what an instance holds and releases at its shutdown (LIF-016), a runtime provider's gate, where it keeps a run's values and what it does with a stop that it cannot carry out now (PRV-025, PRV-011, PRV-021), which name of a machine a machine provider reports (PRV-014), and whether a store's package answers from a copy (SEC-006, SEC-017). That prose is not a document in the sense of this file, and `metadata.description` gives it no meaning to the language (OBJ-018). |
| Schema contract | A contract whose whole `spec` is a schema under the schema profile (CTR-008). A `$ref` may name one by a qualified reference, or by `#name` within one project or package (SCH-015). The reference schemas, and the schemas of documents under [schemas/](schemas/README.md), are Schema contracts of the core package. |
| names a version assigns | The names that a version of this specification states in [names.yaml](names.yaml): the address of the core package, the value of `apiVersion`, the prefix of Conduit's keys, and the names of what `identity` carries (OBJ-024, PRV-022). Only a new version may change them. The last are fixed so that a run or a gate written once works under every engine (PRV-022). For this version the first three are `github.com/shrav-k/conduit/core`, `github.com/shrav-k/conduit/v0` and `io.github.shrav-k.conduit/`, and the others are those that the row `identity` lists. |

## Words the promises do not use

The `_meta` key rows use the prefix defined in [names.yaml](names.yaml).

| Term | Meaning |
| --- | --- |
| grant | Not used for access. The access an open Conduit carries is the operations it lists; it begins when the Conduit is opened and ends when the Conduit is closed (ACC-003, ACC-011). The short form calls its access notation `consumes` (SCT-007). The word keeps only the sense of the protocol's authorization, which follows OAuth 2.1: a grant by which a client obtains a token from an authorization server, as a consumer does from the one that DL13 states (IFC-042, DL13). |
| declaration | Not used for a document. What is submitted is a document, and an instantiation written inside a template is a nested instantiation. The word keeps only the senses of declaring a node lost (PLC-017, PLC-024) and of declaring an extension of the Model Context Protocol, as a client declares Conduit's extension (IFC-036, IFC-037). |
| create | Not used for an operation. An instance is instantiated, and that is done by registering its document. |
| later work | Not part of this version. No operation arranges, through the engine, work that outlasts its invocation: once an invocation has ended, no request that names it as served is dispatched, and the engine dispatches none on its behalf, apart from the read of a secret that SEC-023 makes again, for the caller of the setup that made a connection, once that connection's values are lost, and the read for a provider's run that PRV-026 asks for again after the engine restarts, or the part of it that held that run stops, for the caller of the setup that last asked for that run (ACC-019, IFC-028). Work that is to happen later is asked for later, by an actor, through a Conduit that is open then. An invocation that outlasts its call is something else, and is one invocation (IFC-016). |
| graph, setup graph, retire graph | Not used. An instance's own setup and retirement work is its setup hook and its retire hook (TPL-017, TPL-018), and an operation built from others is an ordinary implementation, a server that makes onward requests (ACC-016). Declared Conduits and entries keep their order (CON-004, POOL-013). An implementation item that states `graph` is rejected (MAN-009). |
| step | Not used. What a setup or a retirement does is its parts (TPL-012, OPS-022). |
| value binding, value reference, `source` of a value reference, output of a graph | Not used; nothing replaces them. Source is the context in which a record or an observation was made (REC-005). An implementation learns its instance's configuration from `config` (IFC-006) or, where it is plain, from what its item's `environment`, `packageArguments` or `headers` take from it (PKG-020). An operation's outputs remain (CTR-002). |
| runtime (declared by a template or a type), `runtimes`, `restoresRuntimes`, restore | Not used. A runtime provider runs an instance's item that is run as its run (PRV-007), and may restart it under its own restart policy (PRV-010). `runtime` is only the standard argument (PRV-006), and a template that writes `runtimes` is rejected (TPL-001, OBJ-019). |
| hold (a handle), the request for no actor | Not used. No instance holds a handle (IFC-011), and every request that the engine sends has a caller (IFC-006). |
| policy, `apply-policy.v1`, `remove-policy.v1` | Not used. Access is narrowed by closing a Conduit and opening a narrower one (ACC-011). Policies are a candidate for a later version; see the [decision records](README.md#where-the-reasons-are). "Policy" is not used for access: it stays only in restart policy, a runtime provider's own term (PRV-010), and in a network policy, which names a machine and never a run (PRV-018, PRV-025). |
| composite, component, component Conduit | Not used. A template that needs two capabilities of one target declares two Conduits (CON-016). |
| constituent, composition, composed requirement | Not used. Several requirements are applied side by side (CTR-005). |
| `obliges`, `narrows`, `appliesTo` | Rejected keys of a Requirement contract (CTR-005). A filter binds the target's implementations alone (CON-022), a requirement of the core package is applied by the engine and any other is a filter (CTR-005), and a requirement is applied only to a Conduit. |
| re-export | Not used. `exports` lists only the package's own documents (MAN-007). |
| rename, `rename.v1` | Not used. A name is fixed once its object is made (OBJ-011): another name means another object. |
| facts, location fact, host, `set-facts.v1`, `location-settings.v1` | Not used for node settings. fact returns only as an evidence kind (PND-004, ENR-005); facts alone never meet the enrollment minimum. A node's labels are fixed under ENR-010. Host is not used for a machine, whose name is its hostname (PRV-014); it stays in shared-host (PLC-013), the host part of an address (NAM-001) and a URL's host (SEC-024, IFC-017, PRV-022). |
| default location, `set-default-location.v1`, `system-settings.v1`, `system-pool.v1` | Not used. The machine provider places an instance that is given no placement (PLC-002, PRV-015), and `system` is of the type `pool.v1`. |
| requirement on placement | Use the label selector (PLC-007). |
| retained result, retrieval tool, `retrieve-result.v1` | Not used. A caller that lost a result repeats its request (OPS-009, OPS-032). |
| withheld, `inProgress`, `interfaceVersion` | Not used; `state`, `withheld` and `interfaceVersion` are not Conduit keys. A result is delivered with its outputs even where its Conduit was closed while it ran (ACC-034); a repeat of an invocation that has not ended reports conflict (OPS-032); and Conduit's keys travel as Conduit's extension (IFC-037). |
| isolation plugin | Not used. A restriction is enforced only where a runtime provider whose contract confines its consumer runs it (ACC-027, PRV-006). |
| location, `location.v1`, location type, stand for | Use node (ruling 42). A node, of the type `node.v1` and made from the core package's template `node`, represents a machine (PLC-008, PLC-026), and `declare-lost.v1` names it in its input `node`. A value tied to a location is a value tied to a node (PLC-020). The word keeps only the senses of the standards that use it: JSON Schema's instance location, and SARIF's `locations` in a diagnostic. |
| machines provider, the engine's own machine | Use the machine provider, whose type offers `machine-provider.v1` (PRV-013), and the engine's own machine provider, its built-in implementation (PRV-003). The computer itself is the machine the engine runs on, and the promises call it that. |
| `label-selector.v1`, `placement` of a Type or an implementation item, `selector` of `place.v1` | Use the schema `labels.v1`, and the key and the input `nodeSelector` (CTR-004, MAN-010, PRV-015). `placement` is only the standard argument (OBJ-013, PLC-001). |
| `location` of `run.v1` | Use `machine`, the hostname and the labels of the machine of the instance's node (PRV-007). |
| counts as declared lost | Not used: the engine declares a node lost when the machine provider reports its machine gone (PLC-024). |
| `secret-reveal.v1`, `reveal-secret.v1` | Use the capability `secret-provider.v1`, which the type of a secret Resource offers (SEC-002), and its one operation `get-secret.v1` (SEC-005). The engine's request for that operation is still the engine's read of a secret (SEC-010). |
| `endpoint` of `run.v1` | Use `url`, the Streamable HTTP URL at which the engine reaches a run, as server.json names it (PRV-007, IFC-017). The prose may still call it the MCP endpoint, as the Model Context Protocol does. |
| `arguments` of an implementation item and of `run.v1` | Use `packageArguments`, keyed by the `name` of a named argument or the `valueHint` of a positional one in the Package's own `packageArguments`; no key binds its `runtimeArguments` (MAN-010, PRV-007). `arguments` is only what an instance document, a nested instantiation or an applied requirement supplies (OBJ-013, NAM-019), and the arguments of a call of the Model Context Protocol (IFC-001). |
| `digest` of a `package` item | Not used: the Package states the hash of its file in its own `fileSha256`, and an `oci` image is pinned by a digest in its `identifier` (MAN-010). A digest is a package's or a submission's (PKG-004, SUB-008). |
| the instance that acted for the caller, the reading instance, `instance` of a record | Not used: a record names the consumer of the Conduit used, in `consumer` (REC-002), and the engine reads a secret for an instance through that instance's own Conduit (SEC-010). |
| `observedGeneration` | Not used: no object has a generation, and a revision is not one (REV-001). |
| origin | Use source, the CloudEvent's `source` of a record and the `source` of a condition (REC-005, OBS-002). The word keeps only the sense of a web origin, as RFC 6454 defines one, which a request on HTTP names in its `Origin` header, and which the engine's server accepts or rejects (IFC-036, DL12). |
| operation identity, `operationIdentity` | Use idempotency key, sent in `io.github.shrav-k.conduit/idempotencyKey` (OPS-008, IFC-023). The convention is that of idempotency keys and outcomes. |

| runtime profile | Use conformance document. |
| trust domain (of a secret) | Use domain of trust. |
| its own setting for restarts | Not used: a runtime provider restarts a run under its own restart policy (PRV-010). |
| node type | Not used: the promises say the type `node.v1` (PLC-008, PLC-028). |
| setup operation, retire operation | Not used: `set-up.v1` and `retire.v1` are themselves the operations, and the setup and the retirement of an instance are each one invocation of one of them (TPL-008). |
| fail over, failover | Not used. Where the engine stops and starts again, on its machine or on another, the promises say that it restarts. An engine can restart on another machine or run as several parts as configured and as its conformance document states under DL17, which gives the outcomes it meets; such an engine sends a header that carries a secret to no `http` URL, whenever the template was registered (SEC-024, SEC-013). A connection that lasts across a restart, whose values the engine no longer holds, has its secrets read again before its next HTTP request (SEC-023, IFC-041), and a provider whose run ended with the engine is run again when the engine first needs it (PRV-026). |

| secret store | Not used.
